# 心动模式（Heartbeat）设计方案

> **落地状态（2026-11-19）**：按老板拍板**只做 iOS**，已按本方案落码；实现细节、调参入口、
> 装机验收清单见 [IOS-HEARTBEAT.md](../ios/IOS-HEARTBEAT.md)。
> 与下面原方案的差异：① 新旧比例做成**设置页滑杆**（默认 1/3，上限 0.6）；
> ② **「不感兴趣」**在播放页理由条和播放列表「即将播放」里都有入口；③ 无缝做到"预取整首 + 本地秒切"（L1），
> 真 gapless（L2，AVQueuePlayer/双播放器）**没做**；④ 桌面/Android 暂不落地。

> 目标：在播放页的播放模式里增加第四种「心动模式」——用户切换后，系统按「下载 > 收藏 > 搜索 > 播放」的口味权重，
> 结合当前播放的歌，算出下一首并在当前歌播放期间完成缓存，播完无缝接上；每切一首就用最新数据重算下一首。
>
> 适用端：Desktop（Kotlin/Compose，FFmpeg + Java Sound）、Android（Kotlin/Compose，MediaPlayer）、iOS（SwiftUI，AVPlayer）。
> 三端 `PlayMode` 语义已对齐，本方案按同一套规则实现，代码各自落地。

---

## 0. 结论先行

1. **能做成，且不需要推荐服务器**：这是单机应用，没有别的用户数据，做不了协同过滤；正确路线是
   **内容画像（歌手/风格/语种/歌名词元）+ 行为权重 + 种子相似 + 规则重排**。项目里 `GuessEngine`
   （`HomeScreen.kt:1402`）、`SongProfile`、`SearchService.searchAll`、`SearchRanker`、`StudioPick`
   已经把 80% 的原料备好了，差的是「流式队列 + 缓存编排 + 重排」。
2. **网易云「心动模式」的算法并不神秘**：官方口径就是「红心单曲 + 开启时正在播放的那首」为种子，
   推荐同风格歌曲，并且**新歌与红心老歌交替出现**。它的体验差异主要来自「种子 + 新旧混合比例 + 推荐理由」，
   而不是某个黑盒模型。
3. **最容易做错的地方不是打分，是链路**：解码/取流/缓存/切歌的时序、URL 过期、预取被淘汰、上一首的慢解析
   回来覆盖新计划（需要 `gen` 代次）。这些在 `App.kt` 里已有对应的坑和惯用法，照抄即可。
4. **建议分三期**：P0 能听（1 深度预取 + 四信号画像 + 歌手召回）→ P1 好听（种子通道 + MMR 去重 + 新旧调度 +
   不感兴趣）→ P2 真无缝（双解码器 gapless）。

## 1. 网易云的「心动模式」与「私人漫游」拆解

### 1.1 心动模式（2018-12-12 上线）

官方介绍（网易云音乐社区《智能播放全新升级：每一刻的你，心动模式都懂》，2018-12-04）：

- 「算法将参考你**红心的所有单曲**和**正在播放的单曲**的数据，更精准地为你推荐相似风格的歌曲。」
- 「心动模式**重点关注开启时正在播放的那首单曲**」——例：开启时在放日文歌《东京》，之后优先推日文歌。
- 「推荐的所有歌曲中，**有一部分是先前红心过的歌曲，其余则是为你发现的新歌**。」
- 位置：挂在「我喜欢的音乐」歌单上，与单曲循环/顺序/随机并列，是**第四种播放模式**。
- 已知差评：重复率高、新歌风格突兀导致「不连贯」。

可确认的产品逻辑 = **种子（开启瞬间的当前曲）+ 红心库 + 新旧混合 + 相似风格**。
可推断的算法结构（无官方披露，按工业界常规）：

```
候选 = 红心歌单（旧爱） ∪ 种子相似歌曲（新欢，通常来自 item-based CF / 标签 / 音频 embedding）
排序 = 种子相似度 + 用户长期口味 + 热度先验
重排 = 新旧交替（避免连续 2 首新歌）+ 同歌手打散 + 近期不重复
```

### 1.2 私人漫游 / 私人 FM

官方 FAQ（《"每日推荐"及"私人漫游"常见问题解答》，2018-09-12）：

- 口味来源：「听歌记录、收藏的歌曲、歌单、歌手、收看的 MV 以及本地歌曲」。
- 实时反馈：「在私人漫游中出现的**切歌、点红心、投入垃圾桶**等操作，也会引起后续推荐歌曲的变化」。
- 负反馈阈值：**30 秒内切掉**会被当作不喜欢；还支持把不喜欢的歌手/风格「关进小黑屋」。
- 形态：无固定歌单、无数量上限、看不到完整队列、可无限听下去；另有场景模式（运动/学习/放松）。

### 1.3 两者差别（决定了我们抄哪个）

| 维度 | 心动模式 | 私人漫游 |
|---|---|---|
| 触发点 | 绑定在「我喜欢的音乐」上的播放模式 | 独立电台入口 |
| 种子 | **强依赖**开启时的当前曲 | 不依赖，纯长期口味 |
| 曲库来源 | 红心库 + 相似新歌 | 全库检索 + 场景 |
| 队列 | 可见（就是一个歌单） | 不可见、无限 |
| 目标 | 舒适地听「熟悉的+像的」 | 探索/发现 |
| 我们对齐 | **本方案 = 心动**（播放页模式位） | 后续可复用同一引擎换调度 |

**结论**：用户要的「播放页列表循环里加一档」在交互上就是网易云的心动模式位置；但用户描述的
「根据下载/收藏/搜索/播放历史猜」更像漫游的口味建模。所以本方案 = **心动的位置 + 漫游的口味模型 + 心动的新旧混合**。
这也正好是它比现有「猜你喜欢」强的地方：猜你喜欢是**离线榜单**（一次算 12 首、刷新才变），
心动是**在线流**（每首重算、跟着当前歌走）。

## 2. 总体架构

```
                      ┌──────────────────────────────────────────────┐
  播放事件/收藏/下载/搜索 │  PlayEventStore（新）                          │
                      └───────────────┬──────────────────────────────┘
                                      ▼
                          ┌───────────────────────┐
                          │  TasteProfile（画像）  │  四通道加权 + 时间衰减 + 饱和
                          └───────────┬───────────┘
                                      ▼
   ┌──────────────┐        ┌───────────────────────┐        ┌────────────────┐
   │ 当前曲（种子）│───────▶│  CandidateSource（召回）│───────▶│ Ranker（排序）  │
   └──────────────┘        │  旧爱池 / 歌手 / 风格   │        │ 打分+惩罚+MMR   │
                           │  / 探索               │        └───────┬────────┘
                           └───────────────────────┘                ▼
                                                          ┌────────────────────┐
                                                          │ MixScheduler（调度）│ 新旧 6:4、同歌手打散
                                                          └─────────┬──────────┘
                                                                    ▼
                                                          ┌────────────────────┐
                                                          │ HeartbeatQueue      │ upcoming = [n1, n2]
                                                          └─────────┬──────────┘
                                                                    ▼
                                     resolveSourceOnce → NextTrackCache.download → READY
                                                                    ▼
                                                          播完 → playFromCache → 重算
```

分层理由：**召回决定上限，排序只做取舍**。只有搜索接口可用的情况下，召回质量靠「歌手/风格通道 + 旧爱池」保证；
打分再花哨，池子里没有对的歌也没用。

## 3. 用户画像（TasteProfile）

### 3.1 四通道权重（用户口径：下载 > 收藏 > 搜索 > 播放）

```kotlin
val W_DOWNLOAD = 1.00
val W_FAVORITE = 0.80
val W_SEARCH   = 0.60
val W_PLAY     = 0.40
```

**关键修正（必须做，否则权重会失效）**：直接按条数加权会被「数量」淹没——500 条播放记录一定压死 3 条下载。
所以每个通道要先做**软饱和**，让通道质量上限 = 它的权重：

```
mass_c = W_c * (1 - exp(-raw_c / K_c))
K: 下载 5、收藏 8、搜索 10、播放 30     // 各通道的自然密度不同
```

这样：下载最多贡献 1.0，播放最多 0.4，顺序恒定；同时「今天下了 30 首」不会把画像一把带偏。

### 3.2 单条事件的贡献

```
w_i = decay(age_i) * quality_i
decay = 0.5 ^ (ageDays / halfLife)      halfLife: 播放 14d、搜索 10d、收藏 45d、下载 60d
quality:
  播放   -> clamp(listenedSec / durationSec, 0.3, 1.0)   // 30 秒切掉 ≈ 0.3
  搜索   -> 搜完点播了结果 1.0；只搜没听 0.4            // 搜索是"意图"，转化才作数
  下载   -> 1.0
  收藏   -> 1.0
```

通道内归一后乘以 `mass_c`，避免条数多的事件主导：

```
contribution_i = mass_c * (w_i / Σ_j w_j) * features(song_i)
```

`features()` 复用 `SongProfile.features`：`singer:×2.0`、`tag:×1.5`、`lang:×1.0`、歌名 bigram `ng:×1.0`。

### 3.3 产出

```kotlin
data class TasteProfile(
    val vec: Map<String, Double>,      // 稀疏内容向量（cosine 用）
    val artist: Map<String, Double>,   // 歌手亲和度，归一化到 0..1
    val tag: Map<String, Double>,      // 风格亲和度
    val lang: Map<String, Double>,
    val seen7d: Set<String>,           // 近 7 天播放过的 key（硬过滤）
    val topTags: List<String>,
    val topArtists: List<String>,      // 召回的查询词来源
    val builtAt: Long
)
```

重建成本 O(事件数)，事件量 ≤ 2000，纯内存计算 < 5ms，**每首歌开头重建一次**即可，不需要缓存失效逻辑。

## 4. 召回（CandidateSource）

| 通道 | 来源 | 查询 | 预算 | 作用 |
|---|---|---|---|---|
| R1 旧爱池 | 收藏 ∪ 下载（本地，零网络） | — | ≤ 30 | 熟悉感、离线兜底 |
| R2 种子歌手 | `SearchService.searchAll(seed.singer, 30)` | 歌手名 | 1 次 | 保证「和当前歌像」 |
| R3 画像歌手 | top 8 歌手的亲和度加权抽样 | 歌手名 | 2-3 次 | 长期口味 |
| R4 风格 | 搜索 `"<歌手> <风格>"`、`"<风格> 经典"` | 组合词 | 1-2 次 | 补量，噪声大，只填空 |
| R5 探索 | `DynamicPool` / 热门 / 编辑精选池 | — | ≤ 10 | 防止越推越窄 |

约束：

- 总候选 **≤ 120 首**，网络调用 **≤ 6 次/首**。用 `artist -> List<Song>` 的 LRU 缓存（TTL 12h），
  稳态每首只需 1-2 次调用（`SearchAndResolve.kt` 已有 in-flight 去重习惯，可复用）。
- 搜索结果必须过 `StudioPick.dedupeByCore`（同曲多版本只留录音室原版）和 `SearchRanker.rank`（压翻唱/Live/消音版）——
  这两个坑项目里已经踩过（《龙文》节目消音版事故）。
- 跨平台同曲只留一条：`platform.name + platformID` 去重之后，再按「歌名+歌手」归并。

## 5. 排序（Ranker）

### 5.1 打分

```kotlin
fun score(x: Song, p: TasteProfile, seed: Song): Double {
    val content   = cosine(p.vec, features(x))          // 0..1 长期口味
    val seedSim   = cosine(features(seed), features(x)) // 0..1 当前种子
    val artistAff = p.artist[x.singer] ?: 0.0           // 0..1
    val known     = when { isDownload(x) -> 1.0; isFavorite(x) -> 0.85; else -> 0.0 }
    val prior     = rankScore(x) / 100.0                // 0..1 平台相关性
    val fresh     = if (x.key !in everShown) 1.0 else 0.0

    return 100 * (0.30 * content + 0.22 * seedSim + 0.18 * artistAff +
                  0.12 * known + 0.10 * prior + 0.08 * fresh)
}
```

`known` 只对 R1 旧爱池生效；新歌通道该项恒 0。权重是先验起点，P1 用离线回放调（见 §10）。

### 5.2 惩罚（乘性，在打分之后）

```
p = 1.0
if (key ∈ 本会话已播)            p = 0        // 硬过滤
else if (key ∈ seen7d)           p *= 0.15
if (同歌手出现在最近 2 首)        p *= 0.30
if (同歌手在最近 20 首出现 ≥ 3)   p = 0        // 硬过滤
if (本会话内 <30s 被切过)         p = 0
if (歌手被「不感兴趣」)           p *= 0.20    // 30 天内
if (topTags ∩ tags(x) == ∅)      p *= 0.55    // 风格断裂，专治"听着听着跳到另一个世界"
```

最后一条是本方案对网易云「新歌风格突兀」差评的正面回应：没有音频特征，就用**标签集合是否相交**做连贯性代理。

### 5.3 多样性重排（MMR）

只按分数排会连续出 3 首同风格同歌手的歌。用 MMR，窗口取最近 5 首：

```
pick = argmax [ score(x) - 0.25 * max_{y ∈ 最近5首} cosine(features(x), features(y)) ]
```

每选出一首就更新窗口，直到选够。效果：既不打散到「随机」，也不让相邻两首太像。

## 6. 新旧混合调度（MixScheduler）

网易云心动 = 红心老歌 + 新歌交替。我们照抄并参数化：

```kotlin
// 默认 6:4（新:旧），可在设置里做成"熟悉度"滑杆
// 用确定性图案而不是概率，便于测试与复现
val pattern = listOf(NEW, NEW, OLD, NEW, NEW, OLD)   // 以 3 为周期：2 新 1 旧
```

- `NEW`：从 R2/R3/R4/R5 排序后的头部取。
- `OLD`：从旧爱池取，**优先「收藏很久没听」**（`favoritedAt` 越久、播放次数越少，分数越高），
  而不是刚听过的那几首——否则「旧爱」变成「最近循环」。
- 旧爱池空了（用户没收藏没下载）→ 自动退化为 100% 新歌，并在界面提示「收藏几首会更懂你」。

这条调度是「像猜你喜欢又不完全是」的关键：猜你喜欢给的是**一批**歌，心动给的是**一条曲线**（熟悉 ↔ 新鲜）。

## 7. 播放链路（这是最容易翻车的一半）

### 7.1 队列语义

三端现状：`playlist: List<Song>` + `playIndex`，`onTrackCompleted()` 里按模式算下一个 index
（Desktop `App.kt:1320`，iOS `PlaybackRules.nextIndex`）。心动模式不要另起一套队列，否则
上一首/下一首/播放列表弹层/桌面歌词全要改。

**做法：心动模式的 `playlist` 就是「本次心动的会话队列」**，语义变成：

```
[已播 ...][当前][即将 n1][即将 n2]      playIndex 永远指向当前
```

- 进入心动：`playlist = [当前曲]`，`playIndex = 0`，种子 = 当前曲。
- 算出一首：`playlist.add(n)`（只 append，不动当前）。
- 播完：`goto(playIndex + 1)`（此时目标已在队列里，`advanceAfterTrackEnd` 的缓存命中分支直接起播）。
- 队列长度上限 200，超了从头裁掉，`playIndex -= 裁掉数`。
- 退出心动：保留队列当普通歌单（用户可能想继续听），或恢复进入前的 `playlist` 快照——建议后者，
  用 `heartbeatEnterSnapshot` 存一份。

### 7.2 状态机与时序

```
IDLE ──enter──▶ PLANNING ──▶ RESOLVING ──▶ CACHING ──▶ READY
                    ▲                                    │
                    └──────── 切歌/换种子/不感兴趣 ◀──────┘
```

时序（用户要求「在当前歌播放过程中算下一首 + 缓存」）：

| 时刻 | 动作 |
|---|---|
| t=0 起播 | 记 `PlayEvent(start)`；`planGen++`；延迟 **2s** 启动 planner（别和本曲取流抢带宽） |
| t=2s | 重建画像 → 召回 → 排序 → 选出 n1、n2（lookahead=2） |
| t≈3-8s | n1：`resolveSourceOnce` → `NextTrackCache.download` → READY；n2 只解析出 URL（不下载，防过期） |
| t=曲长-30s | 看门狗：n1 仍非 READY → 走「紧急模式」：只要流 URL 就够（边播边缓），不再等整首 |
| t=曲长 | `advanceAfterTrackEnd`：命中本地缓存 `playFromCache`；否则用已解析 URL 直接起播；再不行 n2；再不行旧爱池本地文件 |
| 切歌瞬间 | 记录 n1 的 `PlayEvent(end, listenedSec)`，`planGen++`，planner 立刻为新曲重算 |

**`planGen` 代次**是必须的：上一首的慢解析回来时不能覆盖新计划。项目里 `PlayerManager` 已有同款 `gen`
（`PlayerManager.kt:88`），照这个模式做。

### 7.3 无缝切歌的三种档位（按端能力选）

| 档位 | 做法 | 间隙 | 端 |
|---|---|---|---|
| L0 现状 | 播完 → `stop()` → 打开本地文件 → `start()` | 80-300ms，可能"哒"一声 | 三端都能立刻做 |
| L1 近无缝 | 本地文件 + 尾部 120ms 淡出 / 头部 120ms 淡入 + 提前 `open` | 30-80ms，听感连续 | Android/iOS 容易，Desktop 需改 `PlayerManager` |
| L2 真无缝 | 双解码器：距结束 8s 打开下一首解码器预热，EOF 时把 `grabber` 换成下一个、**不关 `SourceDataLine`** | 0ms | Desktop 自研 FFmpeg 引擎可做；Android 换 ExoPlayer（`setMediaItem(next)`+`prepare` 原生 gapless）；iOS `AVQueuePlayer` |

`PlayerManager`（Desktop）改造点：新增 `queueNext(path: String)`，在解码循环里判断
`pos > duration - 8s` 时预开下一个 `FFmpegFrameGrabber`，EOF 时 `grabber = pending` 并继续向同一条
`SourceDataLine` 写 PCM。注意 `gen` 递增与 `pendingSeek` 的清理。

### 7.4 缓存的坑

- `NextTrackCache.MAX_SLOTS = 4`，lookahead 2 + 当前曲 `PlayCache` 已经吃掉 3 格，**再加一首就淘汰掉正在等的**。
  → 提到 6，或给 planned key 加 pin 标记（`prune()` 跳过 pin）。
- **URL 有效期**：QQ/网易直链通常 20-60 分钟过期。所以「n2 只解析 URL」必须限制在 10 分钟内会被消费；
  超过就丢弃重解析。宁可多解析一次，也不要拿死链起播（会触发换源，反而更慢）。
- 下载失败（`download` 返回 null）不要重试超过 2 轮，直接降级到「流式起播」。
- 断网/息屏：`NextTrackCache` 的存在意义就是此时还能连播；planner 在 `NetworkProbe.isReachable() == false`
  时直接跳过召回（省电），只消费已 READY 的队列。

## 9. 边界与降级

| 场景 | 行为 |
|---|---|
| 全新用户（0 数据） | 不硬推「猜」：旧爱池空 + 画像空 → 只用种子通道 + 热门；界面提示「多听几首会更懂你」 |
| 纯净版（`PURE`） | 心动不可用，模式按钮灰掉或点击提示 |
| 队列里只有 1 首（首次进入且解析失败） | 保底「重播当前」而不是静默停播（沿用单曲循环的教训） |
| 全部候选都无源 | 连续失败 3 次（`AUTO_SKIP_MAX`）后暂停心动并 toast，不要连跳烧光队列 |
| 用户开了心动又手动点歌单 | 心动继续，种子跟随手动点的那首（符合网易云行为） |
| 用户切到别的模式 | planner 取消，缓存保留（可能马上切回来） |
| App 重启 | 会话队列不持久化，重算；但 `seen7d` 与 `已播 key` 从 PlayEventStore 恢复，避免重复 |
| 收藏/下载发生在播放中 | 打标失效：只影响 **n2 及之后**，不动已 READY 的 n1（否则刚下好又作废，浪费流量） |

## 10. 指标与验收

先在桌面版做「离线回放」：把真实 `PlayEvent` 序列喂给引擎，按同一套规则重放，对比 shuffle 基线。

| 指标 | 定义 | 目标 |
|---|---|---|
| 30s 跳过率 | 播放 <30s 就切 / 总切歌 | < 25%（shuffle 基线通常 40%+） |
| 完播率 | listened ≥ 90% 占比 | > 55% |
| 正向转化 | 每 100 首产生的收藏+下载数 | > 8 |
| 重复率 | 100 首内同 key 重复 | < 2% |
| 歌手多样性 | 每 20 首的不同歌手数 | ≥ 8 |
| 连贯性 | 相邻两首标签交集为空的占比 | < 10% |
| 预取就绪率 | 切歌时 n1 已 READY / 总切歌 | > 98% |
| 切歌延迟 | 上一首 EOF → 下一首出声，p95 | < 250ms（L1）/ < 50ms（L2） |
| 换源兜底率 | 心动曲目走到第 2/3 级换源的比例 | < 10% |

调参只用两组：`W_*`（四通道）与 `pattern`（新旧比）。别一次调 10 个参数。

## 11. 分期

**P0（能听，约 2 天/端）**
`PlayMode.HEARTBEAT` + 会话队列 + 四通道画像（用现有 `recentSongs`/`favorites`/`downloads`/`searchHistory`）
+ R1/R3 召回 + 打分（不含 MMR）+ lookahead 1 + `NextTrackCache` + 降级链 + 模式按钮。

**P1（好听，约 3 天/端）**
种子通道 R2 + MMR + MixScheduler + 推荐理由 + 不感兴趣/降权 + PlayEventStore 完整埋点 + 离线回放调参。

**P2（丝滑）**
L1 淡入淡出 → L2 双解码器 gapless；lookahead 2；时段/场景（早/晚权重）；iOS 对齐。

## 12. 明确不做

- **协同过滤 / item2vec**：单机无他人数据；除非将来有服务端，否则没有共现矩阵可用。
- **音频 embedding（MERT/CLAP 之类）**：模型体积与端上算力都不划算；`SongProfile` 的歌手/标签/语种已经够用。
- **每 5 秒重算**：没有新信号时重算是纯浪费；只在「切歌 / 收藏 / 下载 / 不感兴趣 / 手动点歌」时失效。
- **把心动做成第二个猜你喜欢页**：心动是**流**（一首一首给、跟着当前歌走），猜你喜欢是**榜**（一批、刷新才变）。
  两者共用画像与打分，但入口、节奏、缓存策略完全不同。

---

## 13. 风险

1. **召回靠搜索接口**：搜索质量决定上限。若某平台搜「歌手名」返回一堆翻唱，需靠 `StudioPick` + `SearchRanker` 压；
   必要时给 top 歌手维护「代表作」小词表（项目里已有 `EditorPlaylist` 这类人工池）。
2. **三端重复实现**：desktop/android 已是两份近似代码（`App.kt` 已出现分叉），心动引擎务必**先写桌面版 + 单测**，
   再原样移植，避免三端行为不一致（iOS 的 `PlaybackRules` 就是为了这个才抽成纯函数）。
3. **真无缝的工作量被低估**：L0→L1 是几十行，L1→L2 要动播放内核。P0/P1 用 L1 交付，L2 单独立项。
