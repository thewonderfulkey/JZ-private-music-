# 发现页 2.0 设计（多源聚合 + BANNER + 新碟）

- 日期：2026-11-26
- 范围：iOS（`ios/JZMusicHelper`），桌面/Android 不做
- 前置：`docs/api/MobiMusic报告-未采用API盘点-2026-11-26.md`（接口与字段实测）
- 状态：**待老板批准**，批准后才进入实施计划

---

## 1 要解决什么

发现页（首页热门/最新单曲/歌单广场/榜单）现在**四个板块共用酷我一家**（`KuwoChart` / `KuwoPlaylist`）。
酷我一旦限流或改接口，整页没有内容。同时：
- 「编辑精选」是本地预置池，已废弃但仍占位；
- 没有运营位（BANNER）、没有专辑维度的内容（新碟）。

## 2 目标 / 非目标 / 反目标

**目标**
1. 每个板块**至少两家**内容源，且是**聚合并列**（两家内容都出现），不是主备切换。
2. 任何一家失败：**只少它那部分**，其余照常显示；整页不空、不弹错。
3. 新增 BANNER（可轮播/可点/可关）与新碟横滑。
4. 删掉编辑精选。
5. 每一块都能标出来源（谁的内容）。

**非目标**
- 不做登录、不碰需要 cookie 的接口；
- 不做专辑详情页（见 §6 的取舍）；
- 不做评论、不做桌面/Android。

**反目标（做了就算失败）**
- 一个源挂了整页空白；
- 用假数据/占位歌曲糊住页面；
- BANNER 跳到外链网页；
- 同一首歌在同一个板块里出现两次。

## 3 方案取舍（已选 B）

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| A 主备切换 | 酷我为主，挂了才换网易 | 网易内容永远看不见；切换时整块跳变 | 否 |
| **B 聚合并列** | 两家都取、合并去重、标来源、各自独立失败 | 请求数翻倍；要处理去重与排序 | **选它** |
| C 只加源不改版式 | 新源塞进现有列表末尾 | 看不出内容来自谁，也解决不了"挂一家整块空" | 否 |

## 4 页面结构（从上到下）

```
[ BANNER 轮播 ]            最多 5 张 · 4s 自动 · 可滑 · 可关 · 只跳站内
[ 我的歌单 ]                现有，不动
[ 最新单曲 ]                酷我每日新歌 + 网易新歌（合并去重，标来源）
[ 猜你喜欢 ]                现有，不动
[ 热门音乐 ]                并列两行：①酷我热歌榜 ②网易热歌榜（各 3 首预览 + 查看全部）
[ 新碟 ]                    横滑；网易新碟；点卡片 = 进专辑页（曲目按专辑 id 拉）
[ 歌单广场 ]                酷我 + 网易混排，卡片标来源
（编辑精选：删除）
```

**板块级降级规则**
- 一家有数据、一家失败 → 渲染有数据的那家；失败源在板块标题右侧显示小字「网易暂不可用」，**不弹错**。
- 两家都失败 → 该板块整体隐藏（不渲染空壳/骨架）。
- 有缓存时先用当日缓存渲染，再后台刷新。

## 5 数据层

- 每板块一个 loader，并发触发，互不 await：
  `SectionData { items: [Song], sources: [SourceState] }`，`SourceState = ok(count) | empty | failed(reason)`。
- **去重键**：`NameMatch.normTitle(歌名) + "|" + NameMatch.singerTokens(歌手).sorted().joined()`；
  同一首跨源只留一条，保留信息更全的一条，并记 `sources: [酷我, 网易]` 用于角标。
- **排序**：最新单曲按 `releaseDate`（有则用）→ 否则保持各源原顺序交替（A1,B1,A2,B2…），避免一边压另一边。
- **缓存**：每板块当日缓存（沿用 `KuwoChart`/`KuwoPlaylist` 的"本地日 + 服务端 pub 日期"口径）；失败**不覆盖**已有缓存。
- 请求预算：每板块每源 8s，单板块总预算 10s；到点用已到的部分渲染。

**榜单页**
- 顶部两个来源并列（酷我热歌榜 / 网易热歌榜），各自 100 首、各自缓存；
- 切换不重新请求（命中缓存直接渲染）；行样式复用 `SongRow`，平台胶囊标来源。

**BANNER**
- 数据：网易 `homepage/block/page` 的 `HOMEPAGE_BANNER`。字段：图片、跳转类型、目标 id。
- 只保留 `targetType` 属于「歌曲」的（歌单跳转见 §6 风险）；最多 5 张，按服务端顺序。
- 交互：4s 自动轮播、可左右滑、点右上角关闭（当次启动内不再出现）；点击进 `SongDetailView`。
- 无数据 → 整块不渲染（不留空位）。

**新碟**
- 数据：网易 `HOMEPAGE_BLOCK_NEW_ALBUM_NEW_SONG` 里的新碟条目（专辑 id / 专辑名 / 歌手 / 封面 / 发行日）。
- 点击：进**专辑页**（见 §7）。专辑页的曲目直接按专辑 id 拉，不靠"歌名搜"。

**专辑页（新增）**
- 入口：新碟卡片；以后歌曲详情的"专辑"也可复用。
- 曲目来源（按优先级，逐级兜底）：
  1. **网易 `api/v1/album/{id}`**（实测匿名可用，返回整张曲目）；
  2. 酷我 `wapi/api/www/album/albumInfo?albumId=`（实测可用）；
  3. QQ `musicu` 的 `GetAlbumSongList`（实测可用）；
  4. 都不行 → 用「专辑名 + 歌手」搜一次，按身份闸过滤后当曲目（降级方案，页面上标「曲目可能不全」）。
- 页面内容：封面大图 + 专辑名 + 歌手 + 发行日 + 曲目数 + 播放全部/随机 + 曲目列表（复用 `SongRow`，带序号）。
- 播放：走现有取流链（哪个源给的就用它的平台 id）。

## 6 取舍与风险（写清楚，免得实施时再吵）

1. **专辑页可以做**（2026-11-26 实测，见 §7 证据）：
   - `/api/album/{id}` 匿名是 **-462**（要 cookie），但 **`/api/v1/album/{id}` 匿名 200**，直接给整张曲目；
   - 酷我 `albumInfo`、QQ `GetAlbumSongList` 也都匿名可用。
   所以"按专辑 id 拿全部曲目"成立，不做"用搜索结果冒充专辑"的临时页。
2. **BANNER 只跳歌曲**：歌单详情页现在是酷我专用（`KuwoPlaylist`），跳网易歌单需要先做通用歌单页——那是另一个工程。第一版 banner 只跳歌曲，歌单跳转等通用页做完再开。
3. **请求数翻倍**：四个板块各多一家 ≈ 多 4–6 个请求/次刷新。用当日缓存 + 只在进入页面/下拉刷新时打，可接受。
4. **去重可能误合**：同一首歌在不同平台时长差 1–3 秒是常态；去重只按「歌名+歌手 token」，不按时长。误合时保留先到的那条（内容不丢，只是少一条重复）。
5. **酷我搜索不可用**（已知）：本设计不依赖酷我搜索，只用它的榜单/歌单/专辑接口。
6. **酷狗专辑接口**目前返回条数对、但曲目名是 null（字段名不同），第一版不用它，留作以后补。

## 7 证据：专辑曲目接口实测（2026-11-26）

| 专辑 | 网易 v1 | 酷我 | QQ | 酷狗 |
|---|---|---|---|---|
| 叶惠美（11） | ✅ 11 首 | ✅ 11 | ✅ 11 | 条数 11、名字 null |
| U87（13） | ✅ 13 | ✅ 12 | ✅ 13 | 条数 13、名字 null |
| 山歌寥哉（22） | ✅ 22 | ✅ 22 | ✅ 22 | 条数 22、名字 null |
| 1989（13） | ✅ 21（Taylor's Version） | ✅ 10（选错碟） | ✅ 10（选错碟） | 19 |

结论：**网易 v1 是首选**（id 直接来自新碟块，不用搜）；酷我/QQ 做兜底。
"选错碟"是搜索匹配问题，走专辑 id 时不会发生。

## 7 验收（可测）

- 断网/单源故障注入：把网易三个接口指向坏地址，发现页仍有酷我内容，且不弹错；
- 把酷我指向坏地址，发现页仍有网易内容（最新单曲/热门音乐/广场）；
- 同一首歌不出现在同一板块两次；
- BANNER 无数据时不占位；有数据时可轮播、可关；
- 新碟点击能出声（且是那张碟里的歌）。
