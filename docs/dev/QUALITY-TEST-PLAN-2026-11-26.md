# 质量与测试计划（2026-11-26）

> 本计划用 `writing-plans` 的纪律写：每一项都有可执行的命令、明确的样本、可验收的产出，
> 不写「适当验证」「补一些测试」这种没法执行的话。
> 配套：`docs/api/线路基线实测-2026-11-26.md`（已有基线）、`docs/api/MobiMusic对照-我们缺什么与兜底建议.md`（缺口清单）。

---

## 0 三条原则

1. **测一个点，必须能改变一个决定。** 测完不改任何决定的测试不做。
2. **先有尺子，再谈结论。** 没有可信的「时长/容器/码率」，所有判断都建在沙子上（这次酷我榜单把 3 分钟写成 12 秒就是教训）。
3. **结论有保质期。** 这些接口一周就可能变。所以测试不是「做完一次」，是「变成每版都能跑的体检」。

## 0.5 已锁定的产品口径（2026-11-26 老板拍板，后续测试与实现都按这个）

### 0.5.1 三条决定

| # | 决定 | 含义 |
|---|---|---|
| 1 | **有源即播是硬约束，音质是偏好** | 只要能拿到整首音频，就必须能播。**任何为了音质把能播的源过滤掉、导致「有歌听不了」的行为，一律按 P0 bug 处理。** |
| 2 | **不做登录** | 产品定位是「无广告、无需登录、能听所有歌、能下所有音乐」。所有取流按**匿名**口径测试与实现；需要登录态的腿（网易官方）不能作为可用兜底。 |
| 3 | **iOS 是唯一主线** | 桌面/Android 暂停优化与开发，不再要求三端同步。改 iOS 时不为桌面/Android 的兼容让步，但也不要顺手改坏它们。 |

### 0.5.2 音质策略：用「补档」解决卡，不用「降档」

老板的原话是：倾向无损；当初全优先 FLAC 导致自动切歌卡住，才不得已整体降一档到 320k。
也就是说——**降档是当时没有办法的办法，不是偏好**。所以要拆成两条约束，而不是二选一：

- **硬约束 A：先有歌听。** 档位只决定「选哪条腿」，不决定「播不播」。没有目标档 → 给能给的最高档并如实标注，**不许判没源**。
- **硬约束 B：起播不卡。** 这是当初降档的真正原因，必须用数据验证现在还成不成立（现在有 2.6s 起播窗口 + 字节代理 + 播放缓存 + 下一首预取，条件跟当初不一样了）。

由此推出的播放策略（2026-11-26 下午定稿，代码见 `c19a420`）：

| 位置 | 策略 | 为什么 |
|---|---|---|
| **在线起播（手动点歌 / 自动切歌）** | **一次解析：第一个过完全部闸门的源立即起播，不等更高档** | 老板定：快 > 音质；先到的是 97k 就播 97k，不为 320k 多等 |
| **预取下一首** | 有 20–30s 预算 → 在**过闸的候选里挑最高档**，整首落缓存 | 音质优先只花在"有时间"的地方，自动连播仍能拿 320k / 0.1s 切歌 |
| **判定没源** | 只有"所有腿都被拒/超时 + 跨平台 + 无损兜底"全空才算 | 滤掉可播源 = P0 |

一句话：**音质优先落在「预取」和「缓存」上；在线起播永远是"先过闸的先播"。**

### 0.6 三条丝滑红线（2026-11-26 老板补充，凌驾于音质之上）

| 编号 | 红线 | 可测定义 | 判定 |
|---|---|---|---|
| **R1** | **不许播一半重头播** | 单次播放内 `AVPlayerItem` 不被替换；`currentTime` 不回退 >1s（用户主动 seek 除外） | 50 次播放里 **0 次** |
| **R2** | **不许明显卡顿** | 播放中出现连续无声 >200ms（缓冲/饥饿）计一次 | 正常网络下 **0 次** |
| **R3** | **必须能自动切歌，且不许久等** | 连续播放 N 首，每首都自动进下一首；切歌间隙 = `didPlayToEnd` → 下一首出声 | 成功率 **100%**；间隙 P50 ≤0.8s、P90 ≤1.5s；**前台 / 后台 / 息屏三种状态都要成立** |

**这三条改变了一个实现结论**：既然 R1/R2 不允许中途换源，那么「用低档起播、再升到高档」这条路**永久关闭**。
音质只能从三个不碰播放器的地方拿回来：

1. **起播前多等一会儿**（窗口内等得到高档就等到，窗口长度待 T5c 标定）；
2. **预取就把高档解析好、并把开头字节预热**（T5d 验证）；
3. **缓存/下载**（上次听过的，这次直接高档）。

代价要说清楚：如果高档在窗口内没来、预取也没命中，**这一整首就是低档**。
这是为丝滑付的价，不许用"中途升档"去换——那会直接违反 R1。

## 1 目标：把「稳 / 准 / 快」变成能验收的数

| 维度 | 指标 | 当前（2026-11-26 实测） | 目标 |
|---|---|---|---|
| 稳 | **R1 重头播次数** | 未测（历史上有过分档替换） | **0 / 50 次** |
| 稳 | **R2 卡顿次数** | 未测（没有测量手段，见 T0） | **0**（正常网络） |
| 稳 | **R3 自动切歌成功率 / 间隙** | 未测 | **100%** / P90 ≤1.5s，三状态都成立 |
| 稳 | **可用即播率**（凡是能拿到整首的歌，都有源可播） | 未测（大概率 100%，但有「过滤掉」的历史风险） | **100%，无例外** |
| 稳 | 每个平台至少有 **2 条独立腿** 能整首出声 | QQ 2（同 CDN）、网易 2、酷我 4（2 条同 CDN）、**酷狗 1** | 四平台都 ≥2，且不同 CDN/鉴权 |
| 稳 | **假活率**（能出字节但不是整首） | oiapi 9/11 = 82% | **0** |
| 稳 | 单腿挂掉后，该平台可用率 | 酷狗挂 = 0 | ≥95% |
| 准 | 错歌率（播放内容 ≠ 标题） | 已知历史事故（《众》/《侧脸》） | **0** |
| 准 | 谎报音质（UI 标的 ≠ 实测的） | 已有 `QualityFacts`，但「整首/试听」没判 | **0** |
| 准 | 假无损（标无损给了 mp3） | 出现过（星海酷狗 1 例） | **0** |
| 快 | 首字节 P50 / P90 | 433ms–1320ms（按腿） | P50 ≤1.0s，P90 ≤2.5s |
| 快 | 2.6s 起播窗口内拿到 ≥256kbps 的比例 | 未测 | ≥90% |
| 快 | **无损优先时的起播耗时 / 卡顿率** | 未测（当初因此整体降档） | 与 320k 优先相差 ≤0.4s，卡顿 0 |
| 快 | 失败腿浪费的时间 | 未测（oiapi 2.2s、网易官方 1.2s） | ≤0.4s/首 |

**这三条不是口号，是门禁**（见 §4）。哪条没达标，就不许声称那方面「稳了」。

## 2 测试分层（六层，越往下越贵、越少跑）

| 层 | 名称 | 跑在哪 | 需要网络 | 单次成本 | 频率 |
|---|---|---|---|---|---|
| **L0** | 断言层（纯函数） | `ios/SelfTest/main.swift` + CI | 否 | 1 分钟 | 每次提交 |
| **L1** | 单腿健康层 | `tools/probes/lines/probe_lines.py` | 是 | 5–35 分钟 | 每次出包前 + 每周全量 |
| **L2** | 编排层（真实播放路径） | 待建 `probe_pipeline.py` | 是 | 15 分钟 | 改排序/口径前后 |
| **L3** | 环境层（时段/网络） | 同一探针，换时间/换网络 | 是 | 10 分钟 | 每周一次晚高峰 |
| **L4** | 端到端层（App 内） | 真机 / 桌面 | 是 | 30 分钟 | 每个出包包 |
| **L5** | 回归门禁 | 以上组合 | — | — | 每次改动 |

**为什么不全在一层做**：L0 是唯一能进 CI 的（不用网、结果稳定）；L1 会过期，只能当「体检」；
L4 最贵但最接近用户感受。混在一起做的后果就是——测了一堆，还是不知道能不能改。

## 3 测试项（T1–T12）

每项固定七栏：**要回答什么 / 怎么跑 / 样本 / 成本 / 产出 / 改哪个决定 / 通过标准**。

### T0 观测补齐（R1/R2/R3 现在**没有**测量手段）

- **要回答**：怎么客观测出「重头播 / 卡顿 / 切歌间隙」？
- **现状**：`PlaybackTrace`（`诊断/trace.log`）已有 30+ 个事件——`didPlayToEnd`、`goTo`、`play`、
  `item ready`、`预取`、`预取命中`、`缓存补档`、`起播低档`、`升档`、`同曲换源`……**切歌间隙和重头播可以直接算**。
  但**没有「卡顿/饥饿」事件**：播放器没有数据可播时，trace 里是空的。
- **怎么补**（只加日志，不改任何行为——这是风险最低的一类改动，但仍按门禁走）：
  1. 字节代理侧记「饥饿」：播放器请求到达时代理拿不到字节、等待 >200ms → 记一条 `饥饿`；
  2. 记 `item 替换`：每次 `replaceCurrentItem` 打一条，带是"失败换源"还是"升档"；
  3. 记 `currentTime 回退`：`installTimeObserver` 里发现回退 >1s 且非用户 seek → 记一条。
- **产出**：能从一份 `诊断/` 里离线算出 R1/R2/R3 三项指标的解析脚本（`tools/ios/analyze_trace.py`）
- **通过标准**：同一段播放，脚本算出的重头播次数与肉眼录屏一致（抽 3 次校准）
- **为什么排在最前**：R1/R2/R3 是红线，但**红线不能靠感觉验收**。没有这三条打点，后面所有"丝滑"都是口头承诺。

### T1 全腿广度扫描（最优先）

- **要回答**：12 条腿各自「整首率 / 假活率 / 固定失败率」是多少？失败是随机的还是按歌固定的？
- **怎么跑**：
  ```powershell
  # 先把 TARGETS 扩到 40 首（12 大牌 / 8 独立 / 6 外语 / 6 新歌 / 8 版权敏感）
  python tools/probes/lines/probe_lines.py --phase stream --gap 0.8 --legs "全部"
  ```
  两轮（间隔 ≥10 分钟），比对失败歌集合是否一致。
- **样本**：40 首 × 12 腿 ≈ 480 次请求
- **成本**：约 35 分钟
- **产出**：`lines_<stamp>.json` + 每腿一张卡：整首率、假活率、固定失败歌清单、延迟分位
- **改哪个决定**：注册表增删（oiapi 摘不摘）、整首性闸阈值、「按歌记忆失败」值不值得做
- **通过标准**（可动手）：每条腿两轮结论一致率 ≥95%；固定失败歌集合可复现

### T2 落月专项 + 档位交叉（回答「能不能全优先无损」）

- **要回答**：
  1. 落月失败的是「随机风控」还是「固定几首」？
  2. **同一条腿、同一首歌，无损与 320k 的成功率差多少、到达时间差多少？**
  3. 「320k 拿不到、flac 拿得到」的歌占多少？（这决定「降档」到底损失了什么）
- **怎么跑**：
  ```powershell
  python tools/probes/lines/probe_lines.py --phase stream --legs "落月" --tier high
  python tools/probes/lines/probe_lines.py --phase stream --legs "落月" --tier lossless
  ```
  对网易（gdstudio）、酷狗（星海）各做一遍同样的两档对照。
- **样本**：40 首 × 2 档 × 3 条腿
- **成本**：约 25 分钟
- **产出**：两档成功率矩阵、**到达时间差分布**（p50/p90）、「只有无损有源」的歌单
- **改哪个决定**：① 落月定位；② 「当前曲全优先无损」到底会不会损失可用性；③ 预取是否只走高音质
- **通过标准**：若「只有无损有源」的歌 >0，则**任何「无损不进播放链」的口径都必须废掉**（与硬约束 A 冲突）；
  若无损与 320k 到达时间差 p90 ≤0.4s，则当前曲也可以直接全优先无损

### T5b 起播卡顿复现（当初降档的真因，必须重验）

- **要回答**：全优先无损，现在还会不会卡？当初的条件（无代理、无缓存、无预取）已经变了。
- **怎么跑**：真机 A/B 对照——同一批 10 首，分别用「无损优先」和「320k 优先」两种排序各播 30 首次，
  记录：起播耗时、前 10 秒卡顿次数、切歌卡住次数。桌面先用同一份测量脚本跑近似值。
- **样本**：10 首 × 2 策略 × 3 轮
- **成本**：约 45 分钟（含真机）
- **产出**：两种策略的起播 P50/P90、卡顿率、「切歌卡住」次数
- **改哪个决定**：**这是唯一能决定「能不能回到音质优先」的数据**
- **通过标准**：无损优先的起播 P90 ≤ 320k 优先 + 0.4s，且卡顿 0 → 可以回到音质优先；
  否则维持「先到者起播 + 后台补档」，并把预取改成只走高音质

### T5c 起播窗口标定（等多久换多少音质）

- **要回答**：窗口从 2.6s 拉到 3.5s / 4.5s，能多拿到多少 320k/无损？多等这 0.9–1.9s 值不值？
- **怎么跑**：探针里统计「目标档到达时间」分布（我们已有每次的 `apiMs` + 首字节时间），
  离线算：窗口 = T 时，命中 ≥256k 的比例曲线（T = 1.6 / 2.6 / 3.5 / 4.5）。
- **样本**：T2/T1 的数据（离线算，不额外发请求）
- **成本**：0
- **产出**：`命中率 vs 窗口` 曲线，以及拐点
- **改哪个决定**：起播窗口取多少
- **通过标准**：找到「再加 1s 只多换 <5% 命中率」的拐点，取拐点前一档

### T5d 预取有效性（音质能不能靠预取拿回来）

- **要回答**：预取到底命中多少？预取只解析 URL、不预热字节，够不够？
- **怎么跑**：真机连续播 20 首，从 trace 里统计：`预取` → `预取命中` 的比例、
  预取命中时起播用的是不是高档、预取**未**命中时的起播档位分布。
- **样本**：20 首 × 2 轮（前台 / 后台各一轮）
- **成本**：约 30 分钟（含真机）
- **产出**：预取命中率、预取对音质的实际贡献率
- **改哪个决定**：预取是否要「只走高音质」、是否要预热开头字节（proxy priming）
- **通过标准**：预取命中率 ≥80%；命中时高档起播比例 ≥90%

### T6b 连续播放 30 首 × 三种状态（R3 的主测）

- **要回答**：前台 / 后台 / 息屏，各连播 30 首，会不会「卡住」？切歌要等多久？间隙从哪来？
- **怎么跑**：真机三组，每组 30 首；导出 `诊断/trace.log`；用 `analyze_trace.py` 算：
  切歌成功率、间隙 P50/P90/max、间隙归因（预取命中 / 未命中 / 解析失败重试）。
- **成本**：约 60 分钟（三组，含息屏等待）
- **产出**：三状态的红线报表
- **改哪个决定**：预取窗口（现在 20–30s 够不够）、后台任务策略、失败重试策略
- **通过标准**：成功率 100%，间隙 P90 ≤1.5s，三状态都成立

### T6c 负面测试：高档晚到时**不许**换源（R1/R2 的守门测试）

- **要回答**：如果高档在起播后才回来，现在的代码会不会偷偷换掉？
- **怎么跑**：探针里人为把高档腿延迟 8s（本地代理延迟注入），播 10 首，看 trace 里有没有
  `replaceCurrentItem` / `升档` / `currentTime 回退`。
- **成本**：20 分钟
- **产出**：R1 违规次数（应为 0）
- **改哪个决定**：`schedulePlaybackUpgrade` 之类残留路径要不要彻底删
- **通过标准**：0 次换 item、0 次回退

### T6d 失败换源的续播位置（唯一允许的"换"）

- **要回答**：播到 1:30 源断了、换源成功，是从 0 重来还是从 1:30 接上？
- **怎么跑**：代理侧掐断连接（模拟源失效），观察换源后的 `seek` 落点与用户听到的位置。
- **成本**：20 分钟
- **产出**：续播位置偏差（秒）
- **改哪个决定**：失败换源是否要强制 seek 回原位
- **通过标准**：偏差 ≤2s；用户听不到"重头播"

### T3 尺子：时长自证（决定其他所有判断可不可信）

- **要回答**：能不能不靠平台自报，直接从音频文件头解出真实时长？
- **怎么跑**：新建 `tools/probes/lines/probe_duration.py`——Range 取前 256KB，按
  `LocalAudioFacts`（`ios/JZMusicHelper/Services/PlaybackCacheRules.swift:194`）同一套逻辑解：
  FLAC=STREAMINFO、MP3=Xing/Info 帧数、M4A=moov/mvhd。
  与平台自报时长逐首比对。
- **样本**：60 首 × 3 条腿（网易/酷我/酷狗各一条，覆盖 flac/mp3/m4a）
- **成本**：约 20 分钟
- **产出**：自证成功率（按容器分）、偏差分布、解不出的原因分类
- **改哪个决定**：整首性闸能不能用「文件自报时长」；若不能，只能退化成「体积 ÷ 平台时长 + 下限」
- **通过标准**：FLAC ≥99%、MP3（有 Xing）≥90%、M4A 头部 moov ≥60% 能自证

### T4 档位诚实度抽检

- **要回答**：标「320k/无损」的，真的是 320k/无损吗？
- **怎么跑**：对 T1 里所有成功项，按容器 + 码率 + FLAC 的 STREAMINFO 采样率/位深复核；
  对「请求 flac 拿到 mp3」的单列。
- **样本**：T1 的成功项（复用，不额外发请求）
- **成本**：0（离线分析）
- **产出**：每腿「假无损率 / 码率不符率」
- **改哪个决定**：UI 要不要显示实测码率（现在胶囊已显示）、档位命名
- **通过标准**：假无损 = 0（当前星海酷狗 1/18）

### T5 编排层：同歌多腿竞速（真实播放路径）

- **要回答**：把 12 条腿按 App 的规则编排起来，30 首歌各自的**选中腿、起播耗时、是否够档**是什么？
- **怎么跑**：新建 `tools/probes/lines/probe_pipeline.py`，复刻
  `URLResolver`/`SourcePicker`/`SameSongCrossResolver` 的排序与 2.6s 起播窗口（只复刻规则，不复制 UI）。
  记录：每条腿何时被调用、何时被判失败、浪费多少时间。
- **样本**：30 首 × 全腿
- **成本**：约 20 分钟
- **产出**：选中腿分布、P50/P90 起播耗时、窗口命中率、失败腿浪费时间
- **改哪个决定**：排序权重、并发数、起播窗口长度、`firstPlayable` 的策略
- **通过标准**：P90 ≤2.6s；窗口内 ≥256kbps ≥90%；选中错歌 0

### T6 本地优先路径

- **要回答**：已下载/已缓存的歌，断网还能不能秒开？会不会反而去请求网络？
- **怎么跑**：桌面版可直接断网实测；iOS 用真机飞行模式。样本 10 首（下载/缓存/未缓存各 3–4 首）。
- **成本**：30 分钟（含真机）
- **产出**：断网起播成功清单、起播耗时
- **改哪个决定**：本地优先是否真的排在最前
- **通过标准**：已下载 100% 断网可播；起播 ≤0.3s

### T7 晚高峰复跑（结论的时段性）

- **要回答**：凌晨的成绩，晚高峰还算数吗？
- **怎么跑**：北京时间 21:00–23:00 跑同一命令（8 条活腿 × 20 首）
- **成本**：约 15 分钟（需等时间窗）
- **产出**：与凌晨基线的逐腿对比（成功率变化、延迟变化、风控码出现率）
- **改哪个决定**：冷却时长、是否做「时段感知」（晚高峰少并发）
- **通过标准**：活腿成功率下降 <10%；若下降 >25%，说明需要时段策略

### T8 网络条件（4G / 家宽 / 弱网）

- **要回答**：换到手机热点、限速 1Mbps、丢包 5% 时，超时与重试够不够？
- **怎么跑**：Windows 用手机热点 + 限速工具；或 `tc`/Clumsy 类工具模拟。样本 10 首。
- **成本**：30 分钟
- **产出**：各腿在弱网下的超时率、重试成功率
- **改哪个决定**：超时值（现在 10–12s）、重试次数
- **通过标准**：弱网下起播成功率 ≥85%

### T9 长挂与过期（下载专项）

- **要回答**：直链约 20 分钟过期，下载暂停 30 分钟还能不能续？
- **怎么跑**：桌面下载 3 首大文件（FLAC 20–50MB），中途暂停 30 分钟再继续；iOS 同流程。
- **成本**：40 分钟（含等待）
- **产出**：续传成功率、失败后的重取行为
- **改哪个决定**：下载是否要「先落盘再校验」的额外策略、过期重取
- **通过标准**：过期后自动重取成功 ≥90%

### T10 身份压力测试（错歌防线）

- **要回答**：同名不同版、翻唱、Live、伴奏、多歌手、繁简、纯音乐，会不会拿错？
- **怎么跑**：构造 40 组易混样本，跑搜索 + 取流 + 身份闸（复用 `NameMatch`/`StudioPick` 口径）。
- **成本**：30 分钟
- **产出**：错歌清单（应为 0）、误杀清单（好歌被挡）
- **改哪个决定**：身份闸阈值、版本词表
- **通过标准**：错歌 0；误杀 ≤5%

### T11 故障注入（拔腿演练）

- **要回答**：一条腿被指向坏地址时，兜底会不会接住？UI 说的是真话吗？
- **怎么跑**：探针里把某腿 URL 改成 `127.0.0.1:9`，观察编排层是否换腿、耗时多少、错误文案。
- **成本**：10 分钟
- **产出**：兜底链行为表
- **改哪个决定**：错误分类、UI 文案、冷却触发
- **通过标准**：单腿坏 → 100% 换腿成功；文案能区分「没源 / 试听 / 网络问题」

### T12 三端一致性 —— **已取消**（桌面 / Android 暂停）

老板 2026-11-26 拍板：iOS 是唯一主线，桌面/Android 已告一段落。
原来这一项是为了「同一首歌三端结果一致」，现在**不再是质量指标**。

保留一条底线：改 iOS 时不要顺手改坏桌面/Android 的编译（仓库里 `desktop/` `android/` 仍在），
但**不再为它们的体验让步，也不再同步补腿**。桌面端「酷狗 0 条源」就此挂账，不做。

## 4 门禁：拿到什么结果才允许动手

### 4.1 研究门禁（开工前，五条全过才准写代码）

1. **可复现**：同一探针跑两次，结论一致（或差异有解释）。
2. **有基线**：要改的那个点，有 before 数字（文件名 + 行号级引用）。
3. **根因到代码**：能指到 `文件.swift:行`，不是「大概是」。
4. **反例清单**：列出至少 3 个「不该被这次改动影响」的场景。
5. **口径先行**：判定写成纯函数 + 断言样例，先在 CI 里红，再实现。

### 4.2 交付门禁（合并/出包前）

1. L0 全绿（`logic-tests` job）。
2. **同探针同参数的 before/after 对比表**（不是「感觉好了」）。
3. **三条丝滑红线不退化**（只要这次改动碰了播放链/缓存/预取/代理，就必须有 T6b/T6c 的数据）：
   R1 重头播 0、R2 卡顿 0、R3 自动切歌 100% 且间隙不升。
4. 无退化：其他腿/平台的关键指标下降不超过 5%。
5. 回滚方案：一个开关，或一次干净 revert。
6. 文档同步：CHANGELOG + 对应口径文档（`docs/ios/*.md` 或 `docs/api/*.md`）。
7. 出包另加：真机清单（见各文档的验收项）+ 包内二进制与上一版不同。

### 4.3 改动类型 × 必须完成的测试

| 想动什么 | 最小前置测试 | 通过标准 |
|---|---|---|
| **任何会让「能播的歌变成没源」的改动** | T2 + T5 | **一律驳回**（硬约束 A：有源即播） |
| **任何碰播放链 / 缓存 / 预取 / 代理的改动** | T0 + T6b + T6c | R1/R2 为 0、R3 100%、间隙不升 |
| 摘 / 换 / 加一条腿 | T1 + 该腿专项两轮 | 该腿整首率 <60% 且有更优替代；同平台仍 ≥1 条 ≥90% |
| 改排序 / 档位口径 | T5 + T5b + T4 | 320k/无损命中率不降；起播 P90 不升；错歌 0 |
| 回到「无损优先」 | T5b + T5c + T2 | 无损优先起播 P90 ≤ 320k + 0.4s，卡顿 0 |
| 改「整首性 / 时长」判定 | T3 + T10 | 自证率达标（§3 T3）；误杀 ≤1% |
| 改冷却 / 重试 | T1 + T7 | 固定失败不再重试；抖动 100% 恢复 |
| 改 UI 诚实标注 | T4 + T5 | UI 显示与实测一致 100% |
| 出包 | L0 + 改动专项 + 真机清单 | 全绿 + 二进制变化 |

**注意**：不是「所有测试做完才能改」。不同改动有不同前置——**改闸门只需要 T1+T3，改排序才需要 T5**。
这条是为了避免「为了稳妥一年不敢动」和「一冲动就改」两个极端。

## 7 现在就能开始的三件，和已拍板 / 仍待定的事

**已拍板（2026-11-26，不再讨论）**

1. 档位：**音质尽量高、有源即播**；任何「过滤掉能播的源」= P0。落地方式是「补档」不是「降档」。
2. 登录：**不做**。所有取流按匿名口径；需要登录的腿不能算兜底。
3. 平台：**iOS 唯一主线**，桌面/Android 暂停。

**能直接开始（不需要再决策）**

1. **T0 观测补齐**：加了「饥饿 / item 替换 / 进度回退」三条只读打点 + `analyze_trace.py`。
   没有它，R1/R2/R3 只能靠感觉验收。
2. **T2 档位交叉**：40 首 × 3 腿 × 两档，先拿到「无损比 320k 差多少到达时间、少了多少可用性」。
3. **T3**：时长自证探针。所有判断的地基，App 里已有 `LocalAudioFacts` 可抄。
4. **T1**：全腿广度扫描（顺手把 oiapi 的 82% 假活率钉死）。
5. **T5c**：窗口标定（离线算，零成本）。

**需要你配合的**：T5b / T6b / T5d 都要真机装包跑（30 首 × 三状态，约 1 小时），
得你那边有机器且愿意按脚本播——这是唯一能验收「丝滑」的路，探针替代不了。

**已完成（2026-11-26 下午，结果见 `docs/api/T1T2T3实测-2026-11-26.md`）**

- **T1**（40 首 × 12 腿）：8 条腿整首率 100%，4 条仍废；落月 25/40（62%）。
- **T2**（同 15 首两档交叉）：无损 6/15、320k 5/15 → **档位不是变量，请求密度才是**；
  「无损更稳」「按歌记忆失败」两条旧结论作废。
- **T3**（尺子）：FLAC 100% / M4A 100% / MP3 94% 能从在线流头部解出真实时长，
  中位偏差 0.76s，最大 93.4s（酷我自报时长）。**整首性闸的判据可以落地了。**

**仍待定（等数据出来再定，不是现在拍）**

- 「无损优先」能不能回到当前曲（等 T5b 真机）。
- 预取是否只走高音质（等 T5 的起播耗时分解）。
- 整首性闸的阈值（T3 已给可行性，具体阈值等真机样本再定）。

## 8 不测的 / 风险

- **不测识曲**：要真实录音 + 各家签名，探针造不出可信样本。要测得单独做一段录音夹具。
- **不测登录态**：产品不做登录（已拍板），所有结论都是匿名口径。网易官方那条腿按「半残」记账，不测它的上限。
- **不测 UI 视觉**：不是这一轮的问题（有专门的录屏整改流程）。
- **不测桌面 / Android**：已暂停，只保证不被改坏编译。
- **不测地区差异**：只有一个出口（澳洲）。国内出口的结论可能不同，报告里必须写清「本结论的出口」。
- **风险**：所有网络测试都会给对方服务器发请求。控制在「一个正常用户刷半小时」的量级，
  同一腿间隔 ≥0.8s，且不在对方明显的限流窗口内反复打。
