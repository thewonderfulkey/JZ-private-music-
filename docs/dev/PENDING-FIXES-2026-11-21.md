# 待修清单（2026-11-21 晚，等老板点头一起修）

> 来源：飞书群 03:18 / 03:30 两段录屏 + 03:19 两张截图。
> 状态：**已定位，未落码**。落码时按下面顺序，一个提交一组，方便回滚。

## ① 崩溃：播放中翻搜索结果，约 90–100 秒后 App 瞬间回桌面

**现象（录屏抽帧确认）**：03:17 那一帧还在「搜索 周杰伦」结果页（底部播放条是《手写的从前-优酸乳为爱告白广告曲》），
下一帧直接是主屏；**没有任何报错、没有过渡动画**——是进程被杀，不是可捕获异常。

**已找到两处能造成这种死法的缺陷：**

1. **封面内存无界（主因）**
   - `CoverImageCache.store()` 把 NSCache 成本写死成 `64*64*4 = 16KB`，与真实解码大小无关
     → `totalCostLimit = 60MB` 形同虚设，真正生效的只有"300 张"这一个张数上限；
   - 全仓**没有任何降采样**（无 `preparingThumbnail` / `CGImageSourceCreateThumbnail`），
     500×500 封面 = 1MB、1080×1080 = 4.6MB 常驻内存；
   - 搜索页每"查看更多"一页 +80 张封面；导入/下载写进 `Cover/` 的旁车是**原图**（1500–3000px，解码 9–36MB）。
   - 300 张 × 0.4–4.6MB = **120MB–1.4GB** → jetsam 杀进程，现象与录屏完全吻合。
2. **越界写（我 2.4.41 引入）**：`LibraryStore.upgradeCoversToAlbum()`
   `guard let idx = favorites.firstIndex(...)` 在 `await` **之前**取值，`await` 之后仍用 `favorites[idx]` 写回
   → 等待网络那 1 秒里收藏列表一变就是 `Index out of range` 硬崩（只在文件级去重合并时触发）。

**修法**
- 封面统一降采样到 300×300（`CGImageSourceCreateThumbnailAtIndex`，避免全尺寸解码）；
- NSCache 按真实字节计费，上限 120 张 / 40MB；收到内存警告清空；
- 写 `Cover/` 旁车前先缩到 600×600；
- `upgradeCoversToAlbum` 在 await 之后**重新查下标**，且只改 picURL；
- 加 `CrashReporter`（未捕获异常 + SIGSEGV/SIGABRT/SIGBUS/SIGTRAP 写 Documents/诊断/）+ 每 15 秒内存采样 + 设置页「导出诊断」。
  → 下一版再复现就能区分 jetsam / 信号崩溃，拿到准确栈。

## ② 去重漏判：「手写的从前」vs「手写的从前-优酸乳为爱告白广告曲」

**实测**：两首都是周杰伦、都 04:57、分属 QQ 与酷我（截图）。
- 一级判定的歌名相似度只有 **5/17 ≈ 0.29**（长副标题把相似度摊薄）→ 远低于 0.75；
- 二级字节指纹：酷我 320k ≈ 11.9MB，QQ cyapi ≈ 97kbps m4a ≈ 3MB，字节天然不同 → 也不命中；
- 灰区入口要求相似度 ≥0.6 → 连「整理重复」都不会出现。

**修法**：加**包含关系判定**——归一化后短标题（≥4 字）是长标题的前缀/子串，且
版本类一致 + 歌手有交集 + 时长都已知且差 ≤4s + 专辑键相等（或一边为空）→ 判同一条录音。
断言要覆盖：`手写的从前 ⊂ 手写的从前优酸乳…` 合并；`爱情 / 爱情转移`、`晴天 / 晴天娃娃`（短名 <4 字）不并。

## ③ 导入：文件都能选中，点「打开」多少次都没反应（主线程被堵死）

**现象（录屏 03:29–03:30 抽帧 + 老板纠正）**：从「下载 tab → ⋯ → 导入本地音乐」进到 `Light Pia…`
（另一个音乐壳子 App）的目录，**所有文件都能选中、全选也正常**；但点右上角「打开」多少次都没反应，
选择器一直停在原地。

**根因（确定，代码级）**：导入是在**主线程**上做重量级 IO，把主线程堵死了。

```swift
// DownloadsTabView.swift:70
Task { @MainActor in
    importReport = await downloads.importAudioFiles(urls)   // ← 整个导入跑在 MainActor
}
```
`importAudioFiles` 虽然是 `async`，但它被 `@MainActor` 的 Task 调用，**非隔离的 async 函数会继承调用方的执行器** →
里面这些同步阻塞调用全都在主线程上：
- `sha256Hex(of:)`：**分块读完整个文件**算 SHA-256（录屏里 95.4MB / 73.6MB / 59.5MB 这些，单个就要几百毫秒到数秒）；
- `FileManager.copyItem(at:to:)`：把整个文件复制进沙盒（几十 MB × 全选的文件数）；
- 每首串行处理，没有进度反馈。

主线程一堵：
- 系统文档选择器是独立进程的远程视图，**画面还在，但"打开"的完成回调要等宿主 App 处理** → 表现就是"按了没反应"；
- 而且我们**没有任何进度 UI**，即使选择器收起了，界面也像死了一样。

**修法**
1. **把导入整体移出主线程**：`Task.detached(priority: .userInitiated)` 里跑（或把 IO 部分放进独立 actor）；
   `items` 的读改写统一 `await MainActor.run { ... }`，主线程只负责最终入库；
2. **加进度与可取消**：`@Published var importProgress: (done: Int, total: Int, name: String)?`，
   界面显示「正在导入 3/20：xxx」+ 取消按钮；用户能看到"在干活"，不会再以为没反应；
3. **大文件预警**：单文件 > 300MB 或总量 > 2GB 时先提示体积再开始；
4. **失败/取消清理**：复制到一半失败要删掉半截文件与旁车，避免留下孤儿；
5. **展示层收口**：同一个视图上现在挂了两个 `.alert` + 一个 `.confirmationDialog` + `.fileImporter`，
   SwiftUI 里多 presentation 叠加容易互相吞事件 → 合并成一个 `enum ImportAlert` 状态机；
   `打开` 也建议不要从 Menu 直接 present（菜单收起动画与弹层抢同一帧），改成先关菜单再延迟 0.2s 呈现；
6. **顺带**：未知扩展名按文件头嗅探（`StreamVerifier.sniffHead`），识别成音频就用正确扩展名导入
   （对方 App 可能只是改了后缀）；加密格式（ncm/kgm/mgg/mflac/qmc*）明确提示不支持。
