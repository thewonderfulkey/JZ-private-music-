# 播放红线打点与验收（R1 / R2 / R3）

> 2026-11-26 老板拍板：**丝滑 > 音质**。三条红线凌驾于档位之上：
> R1 不许播一半重头播；R2 不许明显卡顿；R3 必须能自动切歌且不许久等。
> 本文说明这三条**怎么被客观测出来**，以及怎么出报表。

---

## 1 为什么要有这套打点

这三条以前只能靠"感觉"。老板录屏里「卡一下」「自己跳了」「切歌要等十秒」，我们只能复述，不能量化，
于是每次修完都只能说"应该好了"。

现在 App 往 `诊断/trace.log` 里多打三类事件（**只加日志，不改任何播放行为**）：

| 事件 | 打在哪 | 含义 |
|---|---|---|
| `item 替换` | `AudioPlayer.start(...)`（唯一装 item 的地方） | 这首歌被装进播放器第几次；>1 次带「（同曲重装）」 |
| `进度回退` | `AudioPlayer.installTimeObserver` | **同一个 item 内**、正在播时进度往回跳 >1s（换歌不算） |
| `饥饿` | `PlaybackCache.CacheSession.pump()` | 播放器等字节、等了 ≥200ms |
| `起播阶段` | `AudioPlayer.resolveStream` | ①窗口 / ②先到先用 / ③完整排名 各花了多久、命中还是空 |

阈值集中在 `PlaybackRules.swift` 的 `PlaybackTraceRules`（CI 有断言钉死），
分析脚本 `tools/ios/analyze_trace.py` 用的是同一组数。

---

## 2 三条红线怎么判

| 红线 | 判据 | 通过 |
|---|---|---|
| **R1** | ① 同一首歌被装进播放器 >1 次，且前 10 秒内**没有**失败事件（`源失败`/`缓存文件坏`/`缓存层回退`/`同曲换源`/`缓存续拉解析`）→ 无理由重装；② 任何 `进度回退` | 两者都 0 |
| **R2** | `饥饿` 事件数（每次都已 ≥200ms） | 良好网络 0；弱网允许 ≤1 次/首且不中断 |
| **R3** | `didPlayToEnd` → 下一条 `item ready` 的间隔；没有下一首 = 卡住 | 卡住 0；P50 ≤0.8s、P90 ≤1.5s |

> 2026-11-26 起，报表还多两行：**手动选歌**（`goTo pauseFirst=true` → `item ready`）与
> **解析耗时**（`resolve 结束 Xms`）。这两行回答的是"点一首歌要等多久"，和自动切歌是两回事。

**「失败恢复」不算 R1 违规**：源断了换一条、并 seek 回原位，是允许的——但会在报表里单列，
因为它仍然会让用户"闪一下"，是后续要优化的对象。

---

## 3 怎么取日志

1. 正常播一轮（前台 / 后台 / 息屏各一组，每组建议 30 首）；
2. App 内：设置 → 播放诊断（只读）；或 设置 → 导出诊断 → 「文件」App 里 `JZ 音乐/诊断/trace.log`；
3. 把 `trace.log` 拉回电脑。

---

## 4 怎么出报表

```powershell
python tools/ios/analyze_trace.py 诊断/trace.log
python tools/ios/analyze_trace.py 诊断/trace.log --json     # 给 CI / 表格用
python tools/ios/analyze_trace.py --self-test               # 自检解析器（不读真机日志）
```

输出示例（内置样例）：

```
| 红线 | 指标 | 实测 | 判定 |
| R1 | 播过 3 首；同曲重装 1 次（失败恢复 0 / 无理由 1） | 无理由：稻香×2 | ❌ |
| R1 | 进度回退事件 | 1 次 | ❌ |
| R2 | 饥饿（≥200ms） | 2 次，最长 1200ms | ❌ |
| R3 | 切歌 P50 0.50s / P90 14.10s | 正常 1 / 慢 0 / 卡住 1 | ❌ |
```

退出码：`0` 三项全过；`2` 有不过的项（方便以后接进 CI 或出包闸）。

## 5 已知局限（必须写进每次报表旁边）

1. **饥饿只在走缓存层（字节代理）时能测**。`AudioPlayer` 在拿不到总字节时会退回直连远端 URL，
   那条路没有代理、也就没有 `饥饿` 事件——所以 R2 的覆盖率 = 代理覆盖率，不是 100%。
   报表里要写清"本次有多少首走了直连"。
2. **进度回退**只认「同一个 item 内」的回退（2026-11-26 修：换歌会让进度从 77s 变 0s，
   第一版把换歌误报成违规；现在按 item 身份判定，换了 item 只重新记基线）。
3. **`item 替换` 记的是"装载"，不是"换源"**：首次装载也是第 1 次，只有 >1 次才需要解释。
4. 后台/息屏的 `appState` 只有 前台/后台/未激活 三种，"息屏"通常表现为 `后台`；分组统计时按这个字段分。

---

## 6 与门禁的关系

- 任何**碰播放链 / 缓存 / 预取 / 代理**的改动，出包前必须有 T6b（连播 30 首 × 三状态）的报表；
- R1/R2/R3 任一退化 → 不许出包（见 `docs/dev/QUALITY-TEST-PLAN-2026-11-26.md` §4.2）。
- 阈值改动 = 改验收标准，必须同时改 `PlaybackTraceRules`、`analyze_trace.py`、本文三处。
