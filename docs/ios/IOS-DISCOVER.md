## 1 为什么之前"发现页什么都没有"

上一版发现页只有两块**由本地历史派生**的内容：最近播放、猜你喜欢（其实就是最近播放换个标题）。
新用户没有历史，于是：

```
编辑精选 = 3 个写死的静态分类卡（点不开，卡片下手写"随 P1 接入"）
最近播放 = 空 → 整块不渲染
猜你喜欢 = 空态文案（"多听几首，这里会长出来"）
热门音乐 = 一行占位（"随 P1 接入"）
```

表现出来就是"什么都没接 UI"。**根因不是 API 不通，是这一页根本没有数据源**：
四家平台的搜索/取流/封面/歌词都能用，而「歌单 / 榜单」这一层——**2026-11-17 之前的结论是"一家都没有"，
这个结论对酷狗/QQ/网易成立，对酷我不成立**（见 §2.1）。所以 Android 端那套「内置歌单池 + 种子词搜索合并」
被 iOS 照搬了过来，它仍然是「编辑精选 / 猜你喜欢 / 热门音乐」三块的底座。

> ⚠️ 2026-11-17 修订：上面这句"没有一家提供榜单接口"曾写进本文件与 `DiscoverFeed.swift` 的注释里，
> 实测被推翻——酷我有一整套匿名榜单/歌单/歌手接口，**现在它就是热门音乐的数据源**（§2.1），
> 编辑精选那一排当时仍是原来的 4 张本地池卡（**第三十轮已下线**，换成歌单广场 + 歌手大全，见 §2.3）。

## 2 五条链路（都是真数据，没有编造）

| 区块 | 数据来源 | 失效时的表现 |
|---|---|---|
| **歌单广场**（第三十轮） | **酷我推荐歌单**（`wapi.kuwo.cn/api/pc/classify/playlist/getRcmPlayList`，热门 1754 张 / 最新 9086 张），带封面、创建者、首数、播放量；点开进详情页，**每首歌自带 rid，点开即播** | 失败态 + 「重试」；第一页按本地日缓存，当天只拉一次；`rn=1` 探测到新歌单才重取 |
| **歌手大全**（第三十轮） | **酷我歌手列表**（`wapi.kuwo.cn/api/www/artist/artistInfo`，8849 位；分类 + A–Z，`artistMusic` 取热门歌曲），带头像、粉丝数、歌曲数 | 同上；分类/字母第一页按本地日缓存（只缓存"热门"） |
| **热门音乐** | **① 首选：酷我官方热歌榜**（`kbangserver.kuwo.cn/ksong.s`，匿名、无签名，100 首/日更，模块取前 21）→ **② 兜底：原来那套** 24 个种子词按天取 6 个 → 四平台并发搜索 → `pick` 选 21 首；结果当天缓存进 UserDefaults | 两个来源都拿不到才失败态 + 「重试」；缓存按 `day` 失效（v2 缓存，旧 v1 当天也不复用） |
| **最新单曲**（第二十九轮） | **酷我官方歌单**「每日最新单曲推荐」（`wapi.kuwo.cn/api/www/playlist/playListInfo?pid=1082685104`，匿名、100 首/页，带封面 + 发行日）；按发行日倒序，模块露 12 张卡，「查看全部」进 100 首整页 | 失败态一行 + 「重试」；缓存按**本地日**失效（歌单没有服务端换榜日期），当天只拉一次 |

## 2.1 榜单（酷我官方榜：热门音乐的主数据源）

`热门音乐` 的数据源在第二十轮换成**酷我官方热歌榜**，原来的种子词搜索降级为兜底；样式、页数（21 首 = 3 行 × 7 页）
一律不变，「查看全部」进榜单页看完整 100 首。编辑精选里那张单独的榜单卡已撤掉（老板："把热歌榜换到热门音乐里"）。

| 项 | 值 |
|---|---|
| 榜单目录 | `https://wapi.kuwo.cn/api/pc/bang/list`（36 个叶子榜，本机实测 18 KB / 2.0 s） |
| 榜单歌曲 | `https://kbangserver.kuwo.cn/ksong.s?from=pc&type=bang&id=<mobileId>&pn=0&rn=100`（本机实测 120 KB / 3.5 s） |
| 代码 | `ios/JZMusicHelper/Services/KuwoChart.swift`（解析纯函数） + `Services/DiscoverRules.swift`（`hotModuleSongs`）+ `Views/ChartSongsView.swift`（页面） |
| 匿名性 | 无登录、无签名、无 cookie；`bang/list` 与 `ksong.s` 实测 **https 直连即通**，不需要 ATS 例外 |
| 名次口径 | 模块与榜单页都**保持官方名次**：不重排、不在榜单里做"原版筛选"（`hotModuleSongs` 有断言） |

两个踩过的坑，都写进了 `KuwoChart.swift` 的文件头注释：

1. **两级 id**：目录里 `id`（web，489927）喂给 `ksong.s` 只回 `{}`（2 字节，但 HTTP 200）；
   取歌必须用 `sourceid`（mobile，16）。`Chart` 两个 id 都留着，只有 `mobileId` 上请求。
2. **曲长不在 `duration`**：实测同一批曲 `duration` 是 4 / 1 / 41 / 107 这类值，真曲长在 `song_duration`
   （189 / 272 / …）。用错会直接打穿播放侧的 ±25s 时长闸门（`PlaybackRules.durationToleranceSec`）：
   期望 4s 时真歌被判坏源全网跳歌，反过来 4s 试听片段反而会被当好源。

**榜单曲没有任何封面字段**，所以这一页 100 行的图全靠兜底——顺手把封面链补了：
`CoverResolver` 现在先走**酷我同平台按 rid 取图**（`artistpicserver` 的 `rid_pic`），取不到才跨平台去 QQ 猜。
这条兜底也覆盖了原来那约两成没有 `MVPIC` 的酷我搜索结果（此前全靠 QQ 跨平台兜底）。

`rid_pic` 的响应有三个坑，`CoverResolver.ridPicURL(fromBody:)` 里逐条处理并有断言：

| 坑 | 处理 | 实测 |
|---|---|---|
| 返回的是 `http://` | 统一升 https | iOS 已开 ATS 严格，http 会被系统拦掉 |
| 域名是 `img1.kwcdn.kuwo.cn` | 换成 `img1.kuwo.cn` | 该域**不提供 https**（TLS 直连失败）；同路径在 img1/2/4.kuwo.cn 上 https 200 且字节一致 |
| 个别 rid 返回 `starheads`（歌手头像） | 直接拒收 | 贴到歌曲行上是张冠李戴，比没图更糟 |

**可播性实测**（本轮新增，取 3 个榜各 6 首走现有妖狐酷我通道）：热歌榜 6/6、华语榜 6/6、经典怀旧榜 6/6
全部拿到无损直链——所以榜单页不需要「试听」标记，也没改播放引擎。榜单自带 `payInfo.listen_fragment`
字段（抽取的 10 首里 8 首为 1）在本机链路下不影响取流，暂时只作为解析结果保留，不做 UI 表达。

## 2.2 最新单曲（第二十九轮：酷我官方歌单 + 网易云「艺人新动向」版式）

**来源**：老板把「可以排期做的两条」那张表发过来，第一轮只融进第一条——酷我官方歌单
`1082685104`「每日最新单曲推荐」。版式照**飞书开发群那段录屏**里网易云「推荐」页的
「你关注的艺人新动向」（录屏原文件 `46295530.mov`，13s）。

| 项 | 值 |
|---|---|
| 端点 | `https://wapi.kuwo.cn/api/www/playlist/playListInfo?pid=1082685104&pn=0&rn=100&httpsStatus=1` |
| 匿名性 | 无登录 / 无签名 / 无 cookie；`Referer: https://www.kuwo.cn/` + 移动端 UA，https 直连即通（不需要 ATS 例外） |
| 规模 | 歌单 total **653** 首；`rn` 上限 **100**（给 300 也只回 100），`pn` 从 0 起分页；本页 100 条全部有封面、全部有 `releaseDate` |
| 字段 | `rid` / `name` / `artist` / `album` / `duration`(秒) / `songTimeMinutes` / `pic`(https) / `releaseDate`(yyyy-MM-dd) |
| 代码 | `Services/KuwoPlaylist.swift`（解析 + 排序 + 当天缓存，纯函数可断言）、`Services/DiscoverFeed.swift`（`newReleases` / 状态机 / `loadDaily`）、`Views/DiscoverView.swift`（卡片）、`Views/NewSongsView.swift`（整页） |

**两个数据坑（都钉了断言）**：

1. **曲长**：这页的 `duration` 与 `songTimeMinutes` 在 100 条里 **100/100 一致**，
   不像 `ksong.s` 那样把真曲长塞在 `song_duration`（见 §2.1 坑 ②）。解析仍保留
   「mm:ss 优先、差 >5s 才覆盖秒数」的兜底——历史上确实出现过 `duration=4` 的脏值，
   而播放侧 ±25s 闸门会拿它当期望值。
2. **顺序不是严格的发行日**：官方歌单里第 7 首是 10-11、第 12 首是 2025-08-24。
   模块叫「最新单曲」，所以 `KuwoPlaylist.ordered` **按 `releaseDate` 倒序重排**
   （同日保持歌单原序，缺日期排最后）——调用点不要再排第二次。

**版式（对着录屏那一帧量的，按 390pt 宽折算）**：

```
[圆形封面×3] 最新单曲  每日更新                   查看全部 ›
┌──────────────┬───────────────────────────────┐
│              │ 新单曲                          │   ← 角标
│   方形封面     │ 歌名（白色半粗）                 │
│   100×100     │ 歌手（白 72%）                   │  ▶
│              │ 收录于《专辑》（白 55%）           │
└──────────────┴───────────────────────────────┘
   卡 300×100、圆角 12、间距 12、整排横滑
```

- 右半底色 = **同一张封面糊开**（blur 16）+ 黑色 42% 压暗，白字在任何封面上都读得清；
- 标题左边那叠圆头像，网易云是"你关注的艺人头像"，我们没有关注关系，用**前三首的封面**代替；
- 尺寸走 `@ScaledMetric`（宽 = 高 × 3），AX5 下整卡变大但不截字；
- 点任意一张卡 → 以**这一排 12 首**为队列起播（与最近播放同一口径，不是单曲循环）。

版式预览稿（浏览器直接打开，真数据）：[mockups/new-songs-v1.html](mockups/new-songs-v1.html)
/ [PNG](mockups/new-songs-v1.png)（`tools/ios/gen_new_songs_mockup.py` 重新生成）。

**缓存与"同进度"**：

- 老板："同样保持加载一次当天不再加载，除非第二天刷新，和酷我的接口保持同进度。"
  → `DiscoverFeed.loadDaily()` 把**热门音乐与最新单曲合成一趟**（并发），共用本地日边界：
  当天已有缓存 → 一个请求都不发；跨天 / 下拉刷新 / 回到前台 → 一起重取。
- 缓存 key `kw_playlist_cache_v1_1082685104`（UserDefaults JSON，100 条 ≈ 40KB），
  存 `day` + `releases`；`init` 里**同步读盘**，第一帧就有卡，不闪骨架。
- 手上已有昨天那页时不亮骨架：重取是后台行为，拿不到就继续显示旧的（失败只在"一条都没有"时报）。

## 2.3 歌单广场 + 歌手大全（第三十轮：编辑精选下线）

方案 / 版式依据：[IOS-SQUARE-ARTIST-PLAN.md](IOS-SQUARE-ARTIST-PLAN.md)（含 5 屏真数据预览稿）。

| 项 | 歌单广场 | 歌手大全 |
|---|---|---|
| 列表接口 | `getRcmPlayList?pn=1&rn=30&order=hot\|new` | `artistInfo?pn=1&rn=30&category=<id>&prefix=<A-Z>` |
| 总量 | 热门 **1754** / 最新 **9086** | 全部 **8849**（分类 total 见方案 §3） |
| 详情接口 | `playListInfo?pid=&pn=0&rn=100`（带 rid / 封面 / 创建者） | `artistMusic?artistid=&pn=1&rn=50`（周杰伦 1707 首） |
| 代码 | `KuwoPlaylist`（Summary/Detail）+ `SquareFeed` + `PlaylistSquareView` / `PlaylistDetailView` | `KuwoArtist` + `ArtistFeed` + `ArtistDirectoryView` / `ArtistDetailView` |
| 模块 | 横滑 132 封面 + 播放量角标，露 8 张 | 横滑 5 个 64 圆头像 + 粉丝数 |
| 整页 | 热门 / 最新 chips + 双列封面墙，30/页自动加载 | 分类 chips + A–Z + 三列头像墙，30/页 |
| 详情 | 112 头图 + 播放全部 + 统一 SongRow（点开即播） | 88 头像 + 粉丝 + 播放全部 + 热门歌曲 50 行 |

**缓存（老板："当天只拉一次，和酷我接口刷新时间一致"）**：

- 两个模块的第一页都进发现页那一趟（`DiscoverView.loadEverything()`：`DiscoverFeed.loadDaily()` +
  `SquareFeed.loadIfNeeded()` + `ArtistFeed.loadIfNeeded()` 并发）；下拉刷新 / 回前台四块一起重取。
- 歌单 / 歌手接口**没有 `pub` 一类的服务端刷新日期**，所以锚点是**本地日**（与最新单曲同口径）；
  `SquareFeed.probeNewestIfNeeded()` 用 `rn=1`（约 1KB）问一次最新歌单首条 id，**变了才重取**整页，
  节流 30 分钟——这是老板要的"当天新上架的歌单立刻能看到"，而不是每次打开都整页重拉。
- 缓存键：`kw_square_v1_hot` / `kw_square_v1_new`（第一页 30 条）/ `kw_artists_v1_<category>`（热门页）；
  第 2 页起只在内存。数字统一走 `CountFormat.short`（万 / 亿）。

**取舍**：按曲风标签取歌单（`getTagPlayList`）匿名返回 `total: 0`（网页版同样打不开），
所以广场只做 热门 / 最新 两个排序，**不做曲风筛选**（不做假筛选）。

## 3 挑选口径（与 Android 同口径，全部钉在 CI 断言里）

| 规则 | 为什么 | 代码 |
|---|---|---|
| **只要原版**：`name == coreName(name)` | 榜单里出现「夜曲 (Live)」「夜曲 - DJ版」= 一眼假 | `DiscoverRules.pick` |
| **同曲去重**：按 `coreName` 归并 | 四个平台都返回同一首歌，不去重会连续 4 条一样 | 同上 |
| **同歌手 ≤2 首**、**同歌手不相邻** | 种子词里有 6 个周杰伦，不限制会变成"周杰伦榜" | `pick`（第二遍才放宽相邻，保证凑得满） |
| **核心歌名**：去括号内容、去 Live/DJ/翻唱/伴奏/纯音乐 等后缀、去尾部连接符 | 同一首歌的十几种写法要归成一个 | `DiscoverRules.coreName` |
| **每日轮换**：`rotate(pool, day, take)` | 编辑精选的"每日换一批"，同一天多次打开稳定 | `DiscoverRules.rotate` |

## 4 已知取舍（都写进代码注释了）

1. **「播放全部」只预热 5 首**：一首一次四平台搜索，20 首要一分多钟，用户会以为卡死。现在凑够 5 首就起播，其余点哪首解析哪首。Android 是"后台并发补队列"，那需要引擎支持队列追加，留下一步。
2. **编辑精选的池子没有 Android 的 DynamicPool**：Android 每天往池子里注入新搜到的歌（上限 2000、近 7 天不重推）。iOS 现在只做日期轮换——内容会重复，但不至于空。
3. **热门音乐 = 榜单优先 + 种子词兜底**（第二十轮改）：真榜拿得到就整块用榜（副标题写「酷我热歌榜 · 每日更新」），
   拿不到就回落到"四平台合并 + 原版优先"（副标题写「四平台合并 · 每日更新」）。两个来源不要混成一个口径：
   一个是平台给的排名，一个是我们自己挑的。**排名顺序一律不做二次筛选**——榜单页与模块都按官方名次显示。
4. **编辑精选歌单页要在进页面时把 20 首解析成真实 Song**（第二十轮起）：池子里只有「歌名 + 歌手」，
   所以封面/专辑/收藏都必须等解析。现在是并发 3 渐进补（解析出一首填一格），代价是这一页
   首屏会有几秒"占位行 → 正式行"的替换过程；换来的是行内有封面、歌手·专辑、平台、时长、收藏。
4. **猜你喜欢的推荐理由**目前只有一句"根据你最近的播放"，没有 Android 的"和你常听的《X》同年代"式文案（那需要 SongProfile 向量计算）。
5. **类别主题色**（`0xF0B45A` 等 4 个）是设计令牌之外唯一的颜色来源，因为类别色属于数据；卡片里没有 AI 海报，用同色渐变块。

## 5.1 打开就要快：这一页的缓存全在这（第二十一轮，2026-11-18）

老板反馈：「一打开所有需要加载的东西都非常慢，能不能加载一次以后长时间不用再加载？
热门音乐一天中定死的，就不用每次打开都加载了吧」+「编辑精选也是，连整个条目都要加载，
能写死的写死」。这一轮把"每次打开都重新拉"的四处全改成**本地优先**：

| 数据 | 之前 | 现在 | 失效条件 |
|---|---|---|---|
| 热门音乐（当日 21 首） | 每次冷启动先闪骨架屏，再拉榜单 | `DiscoverFeed.init` **同步**读当天缓存 → 第一帧就有内容 | 跨天 |
| 猜你喜欢（6 首） | 每次打开都四平台搜一遍 | 当天 + 「最近播放指纹」缓存（`DiscoverRules.guessSignature`，前 3 首 id）；指纹没变**一个请求都不发** | 跨天 / 指纹变 |
| 榜单页（100 首） | 每次进页面都请求 `ksong.s` | `KuwoChart` 整页写进当天缓存，进页面直接铺；`fetchPage` 成功时自动写 | 跨天 / 点「重试」强制刷 |
| 最新单曲（100 首，第二十九轮） | —（新模块） | `KuwoPlaylist` 当天缓存（`day` + `releases`），`DiscoverFeed.init` 同步读盘；与热门同一趟加载 | 跨天 / 下拉刷新 |
| 歌单广场第一页（30 张，第三十轮） | —（新模块） | `kw_square_v1_hot` / `kw_square_v1_new`，`SquareFeed.init` 同步读盘；`rn=1` 探测到新歌单才重取 | 跨天 / 新歌单上架 / 下拉刷新 |
| 歌手大全第一页（30 位，第三十轮） | —（新模块） | `kw_artists_v1_<category>`（只缓存"热门"），`ArtistFeed.init` 同步读盘 | 跨天 / 下拉刷新 |
| 封面图 | 只有内存缓存，杀进程即没 | `CoverImageCache` 三层：内存 → **磁盘**（`Caches/cover-images`，600 张，按最后访问淘汰）→ 网络 | 最多 600 张 / 系统清 Caches |

要点两条：
1. **能同步读的一律同步读**（`UserDefaults` / Documents 里的 JSON，几毫秒），别再"先骨架屏再等网络"；
2. **请求只发一次**：缓存命中时连"后台刷新"都不做——这类数据（榜单/猜你喜欢/预设歌单的映射）
  一天甚至一季才变一次，多刷一次只是让首屏更慢。

## 6 装机要看的 6 件事

1. 打开 App 停在发现页：搜索下面第一块是**歌单广场**（132 封面横排，封面左下「♫ 91.2万」角标），
   第二块是**歌手大全**（5 个圆头像 + 粉丝数）；编辑精选那 4 张文字卡应该**没有了**。
2. **最近播放与猜你喜欢之间**应有「最新单曲」：标题左边 3 个圆封面，右边一排横滑宽卡
   （方形封面 + 糊开的右半 + 「新单曲」角标 + 歌名/歌手/收录于《专辑》+ 右下播放三角），
   卡片点下去直接出声；标题右侧「查看全部」→ 100 首整页（统一行样式 + 播放全部）。
   同一天反复进出发现页，这一排**不应再转圈**（当天缓存）；下拉刷新才会重取。
3. 点歌单广场「查看全部」→ 广场页：热门 ↔ 最新可切，双列封面墙，滑到底自动加载；
   点任意一张 → 详情页（112 头图 + 播放全部 + 100 行 SongRow），**点开立刻出声**（这些歌自带 rid）。
4. 点歌手大全「查看全部」→ 歌手页：分类 chips + A–Z，点周杰伦 → 88 头像 + 「166.4万粉丝 · 1707 首」
   + 热门歌曲，「播放全部」出声。字母条点 Z 应只剩 Z 开头的歌手。
5. 点热门音乐右侧「查看全部」→ 榜单页：页头「100 首 · 更新 <日期> · 酷我官方榜」+「播放全部」，
   100 行是**统一行样式**，**每行都有封面**（榜单没有封面字段，全靠 rid_pic 兜底）。
6. 播一首听几秒，等它自然播完跳下一首（或手动切歌）：**悬浮栏的封面、歌名、歌手必须同时换**。
   （第二十轮修的 bug：半壶纱播完切到奢香夫人时，悬浮栏封面还停在上一位。）
