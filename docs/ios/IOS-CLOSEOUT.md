# iOS 收尾项：队列追加 / 本地文件播放 / 设置开关生效 / 编辑精选不重复

> 状态：**已落码、CI 编译与纯逻辑断言通过**（2026-11-16）。真机未验（Windows 无设备）。
> 这四项是 P5 之前的"补漏"：它们不改产品形态，但每一项都对应一个用户能感觉到的缺陷。

---

## 1 队列追加（让「播放全部」真的能补满）

**之前**：发现页「播放全部」只解析 5 首就起播，剩下的永远进不了队列——听到底就停了。

**现在**：`PlayerEngine.appendToQueue(_:)` 在后台把其余曲目逐首解析、解析一首补一首：

```
点「播放全部」→ 解析前 5 首 → 起播（不等其余）
                  └─ 后台继续解析 6…20 → appendToQueue 逐首追加
状态行："队列已就绪 5 首，正在补齐其余…" → "队列已就绪 20 首（整张 20 首）"
```

为什么先起播 5 首再补：一首歌一次四平台搜索，20 首串起来要一分多钟，用户会以为卡死。
追加而不是"重新起播"：`appendToQueue` 只往队尾加，不打断当前播放，也不重复加已在队列里的歌。

## 2 下载列表播本地文件

**之前**：下载完的歌点开还是走在线取流——离线时点了没声音，流量也白省。

**现在**：`DownloadManager.localFileURL(for:)` 给出已下好的文件路径，播放引擎在 `loadCurrent` 里**优先播本地文件**：

```
播放一首歌
  → 本地有文件？→ AVPlayerItem(fileURL)  【状态行：本地文件 · 歌手 - 歌名 […].flac】
  → 没有        → 走原来的三级取流链
```

副作用（好的那种）：任何入口点已下载的歌都省一次解析，起播更快。

## 3 设置里的开关真正被引擎消费

之前这四个键只是"存起来了"，引擎没读——设置页改了也没反应。现在：

| 设置项 | 之前 | 现在 |
|---|---|---|
| 无源自动换源 `autoFallback` | 恒定三轮重试 | 关掉 → 只解析一轮（不空等 2s/2.5s/3s） |
| 跨平台补源 `crossPlatformBackfill` | 恒定调用 | 关掉 → 不做同曲跨平台解析 |
| 自动跳歌 `autoSkipDeadSongs` | 恒定按 3 首 | 关掉 → 跳 1 首就停 |
| 跳过上限 `skipLimit` | 硬编码 3 | 读设置值（1…N），`PlaybackRules.shouldStopAfterSkips(_:limit:)` |

`PlaybackRules` 仍是纯函数（新增的是带 `limit` 的重载），所以 CI 能断言"上限 1 时第 1 首就停""上限 0 按 1 处理"。

## 4 编辑精选不再重复推同样几首

**之前**：`rotate(pool, day, 20)`——30 首池子按天滑窗，第 8 天开始就会反复出现同一批。

**现在**：`DiscoverRules.pickByRecency`——按"上次展示日"升序挑（没展示过的最优先），
展示过就记下当天（`discover_shown_days_v1`，key = 类别|歌名|歌手）：

```
今天第一次进「华语经典」→ 从没展示过的优先 → 20 首
点「换一批」→ offset 转一格 → 换出另一组
明天再进 → 昨天展示过的排到后面 → 自动换新
```

这是 Android `DynamicPool` 的**简化版**：不做"每日从搜索结果注入新歌进池"（那需要一套 2000 条的池子与淘汰策略），
但"同一批歌不会反复推"这个用户能感觉到的部分已经做到。

## 6 装机要试的 4 件事

1. 发现页「播放全部」→ 先出声 → 播放页队列应逐首变长（`… 20 首`），听到底不要停。
2. 下载一首歌 → 开飞行模式 → 从下载页点它 → **应能播**（状态行写「本地文件 · …」）。
3. 设置里关掉「跨平台补源」→ 搜一首冷门歌 → 状态行应很快给"没有可用的播放源"，而不是等 40 秒。
4. 设置里把「跳过上限」改成 1 → 连续点几首无源的歌 → 第一首之后就应停下。
