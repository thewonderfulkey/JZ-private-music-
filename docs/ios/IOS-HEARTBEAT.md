# iOS 心动模式（Heartbeat）：第四种播放模式

> 状态：**已落码**（2026-11-19）。CI 的 `logic-tests` 会编译 `HeartbeatRules.swift` 并跑断言；
> **没有在真机上验证过"切歌到底顺不顺"**——本机是 Windows，出声/无缝只能装机看（§7）。
> 只有 iOS 有这一档；Android / 桌面版没有对应实现。

---

## 1 它是什么（和「猜你喜欢」的区别）

| | 猜你喜欢（发现页） | 心动模式（播放页） |
|---|---|---|
| 形态 | **榜**：一次算 12 首，刷新才变 | **流**：一首一首算，跟着当前这首走 |
| 触发 | 打开发现页 | 播放模式切到「心动模式」 |
| 输入 | 最近播放的歌手关键词 | 下载 / 收藏 / 导入歌单 / 搜索 / 播放**五通道** + 当前曲做种子 |
| 输出 | 12 首列表 | 下一首（播完自动接上），带一句推荐理由 |

网易云「心动模式」的官方口径是「红心单曲 + 开启时正在播放的那首」为种子、新旧交替（见
[官方介绍](https://music.163.com/web/pctopic?black=1&id=43237122)）。这里抄的是这套**产品逻辑**，
不是它的模型：本 App 单机、没有别的用户数据，做不了协同过滤，走的是「内容画像 + 行为权重 + 规则重排」。

老板 2026-11-19 拍板的三条：

1. **只做 iOS**；
2. 五通道权重 **下载 > 收藏 > 导入歌单 > 搜索 > 播放**（第四条「导入歌单」是同日追加：
   老板要让心动模式也吃导入进来的歌单）；
3. 新旧比例在**设置页做滑杆**，并且要有**「不感兴趣」**入口。

## 2 算法

### 2.1 五通道画像（`HeartbeatRules.buildProfile`）

权重：下载 **1.00** / 收藏 **0.80** / 导入歌单 **0.70** / 搜索 **0.60** / 播放 **0.40**。

**关键：先饱和，再加权。** 直接按条数加权，500 条播放记录一定压死 3 条下载，权重顺序就名存实亡：

```
mass_c = W_c · (1 − e^(−distinct_c / K_c))
K: 下载 5 · 收藏 8 · 导入歌单 120 · 搜索 10 · 播放 30      // 各通道的自然密度不同
```

通道质量上限 = 它自己的权重；条数再多也越不过去（`SelfTest` 有一条"30 次播放 vs 3 次下载，下载赢"钉着）。

单条事件再乘：

- **时间衰减** `0.5^(ageDays / halfLife)`，半衰期：下载 60 天 / 收藏 45 天 / 导入歌单 30 天 /
  搜索 10 天 / 播放 14 天（下载收藏是长期口味，搜索播放是当下口味；歌单按**导入时间**老化）；
- **质量**：播放 = `clamp(已听秒 / 总时长, 0.3, 1.0)`；搜索 = 搜完真的听了一首能对上的歌 `1.0`，只搜没听 `0.5`。

产出：`vec`（歌手 2.0 / 风格 1.5 / 语种 1.0 / 歌名 bigram 1.0 的稀疏向量）、`artist` / `tag` 亲和度、
`lastPlayed`、`seen7d`、`searchHints`、`topArtists` / `topTags`。**每选一首歌重算一次**（O(事件数)，≤600 条）。

### 2.2 打分（0~100）

```
score = 0.34·口味余弦 + 0.26·歌手亲和 + 0.12·旧爱(下载 100 / 收藏 85 / 导入歌单 72)
      + 0.08·平台序 + 0.08·新鲜度 + 0.06·搜索命中 + 0.06·种子相似
```

**种子只占 0.06**（2026-11-19 老板反馈后从 0.22 降下来）：当前这首很可能是随手点的，
把它当第二权重会让"随便点一首"带偏后面十首。现在它只在两种情况下起作用：
① 画像是空的（冷启动）时当召回词；② 两首歌几乎同源时当一句推荐理由（阈值 70）。

理由按最强证据取，优先级：下载 > 收藏 > 导入歌单 > 搜索 > 常听歌手 > 种子 > 探索。
文案例如「你下载过 林俊杰 的歌」「来自你导入的《我喜欢的音乐》」「和《晴天》同风格」「搜过「夜曲」」。
（导入歌单的候选在 `known` 档位拿 72 分，比收藏 85 弱一档：整张歌单不一定首首都爱听。）

### 2.3 惩罚（乘性）

| 条件 | 系数 |
|---|---|
| 本会话已播 / 不感兴趣 / 队列里已有 | **0**（硬过滤） |
| 同歌手在最近 20 首里出现 ≥3 次 | **0** |
| 同歌手在最近 2 首里 | ×0.30 |
| 近 7 天听过 | ×0.15 |
| 不感兴趣的歌手 | ×0.15 |
| 与最近 5 首的风格标签完全不相交 | ×0.55（治"听着听着跳到另一个世界"） |

### 2.4 多样性（MMR）

```
pick = argmax [ score − 22 · max_{最近 5 首} 余弦(候选, 那首) ]
```

在"分数高"和"跟刚才几首不像"之间折中，避免连着三首同款。

### 2.5 新旧混合（设置页滑杆）

`oldShare`（0 ~ 0.6，默认 1/3）决定"旧爱（收藏 / 下载过）"占比。用 Bresenham 式累加而不是抛硬币：

```
wantsOld(position) = ⌊position·share⌋ > ⌊(position−1)·share⌋      // position 从 1 起
```

`1/3` → 新 新 旧 新 新 旧；`0.5` → 新 旧 新 旧；第 1 首永远是新的。比例精确、不会连着 4 首旧歌。
旧爱池里 48 小时内听过的不算怀旧，并按「多久没听」加分（最多 +18）——翻出来的是**很久没听的老收藏**，
不是最近循环的那几首。

### 2.6 冷启动 / 兜底：热歌榜（"大家都在听"的定义）

新用户没有任何下载 / 收藏 / 搜索 / 播放数据时，画像为空，前三路召回都出不来东西。这时用**平台官方热歌榜**：

- **数据源**：酷我「热歌榜」（`KuwoChart.Chart.hot`，`mobileId=16`，平台按热度每日更新，100 首）。
- **为什么是榜单而不是播放量**：真实播放量拿不到，接口给的 `play` 数经常缺失/不可信；榜单是平台把
  播放、收藏、搜索综合算过之后的结果，是"大家爱听"最接近的可获得代理。
- **为什么不用「四个平台都能搜到」当热度**：那会偏向老歌——经典曲库四平台全有，但当下没人听。榜单名次才反映"当下"。
- **怎么筛**：取前 60 首 → 只留原版（`DiscoverRules.pick`：去 Live/翻唱/伴奏、同歌手 ≤2）→ 前 20 首；
  再剔掉本轮已算的、本会话听过的、**7 天内听过的**、以及「不感兴趣」——放的是"没听过的热门"，
  不是"把榜单从头再放一遍"。
- **怎么取**：本进程缓存 → 酷我自己的按日缓存（零请求）→ 才真拉一次（20s 超时）。
- **理由文案**：`热歌榜第 N 名`（名次就是解释，不凭空说"热门"）。

触发条件有两处：① 画像为空（冷启动）——此时**先试种子歌手**（用户是从某一首点进来的，同歌手最相关），
搜不到才退热歌榜；② 新歌池与旧爱池都空（数据太少或全都听过）。

### 2.7 连热歌榜都没有怎么办：四级梯子

"有没有足够数据"不是看"候选 ≥ N 首"，而是看**至少有一首能解析出可播的流**。
所以每一级都不是"有候选就算过"，而是"真取到流才算过"；一级过不了就往下一级走：

| 级 | 池子 | 代价 | 会用"听过的"吗 |
|---|---|---|---|
| ① | 画像召回（新歌 / 旧爱 = 收藏+下载+**导入歌单**；冷启动先试种子歌手） | ≤3 次搜索 | 不会 |
| ② | 酷我热歌榜（缓存优先，见 §2.6） | 0~1 次请求 | 不会（7 天内听过的剔除） |
| ③ | 自家资料库：收藏 + 下载 + 最近播放 | 零网络 | **会**（最久没听的排前面） |
| ④ | 内置精选池 `DiscoverCatalog.hotSeedWords` → 搜索 | 2 次搜索 | 不会 |

④ 之后播放器还有最后一手：**退回队列顺序**——队列里还有别的歌就按列表继续，只有一首就重播这首；
播放页理由条会显示「暂无新歌，先按列表继续」。只有连一首能播的都没有（连续 3 首无源）才真停。

第 ③ 级"允许重播"是刻意的：走到这一步说明"没听过的"已经枯竭。对用户来说，
"放一首我喜欢的老歌"远好于"放着放着停了"——这是产品取舍，不是算法退化。
整条梯子有时间上限（20 秒），不会变成"选歌卡住"。

**导入歌单（第四十三轮）**：它既是第五通道（影响新歌召回用的 top 歌手/口味向量），
也是①旧爱位的候选来源（`HeartbeatEngine.playlistCandidates`，理由写「来自你导入的《歌单名》」）。
所以"没下载、没收藏、没搜索，只导了几张歌单"的用户也能跑心动模式：画像不空，新歌位按歌单里的歌手搜，
旧爱位直接放歌单里的歌。歌本身带平台 id，取流走原有适配器，不需要再搜索。

## 3 播放链路

```
切到心动模式
  └─ activate(seed = 当前曲)
       ├─ 起播（start）→ 记播放事件 → 2 秒后开始规划（避开本曲取流）
       ├─ 画像 → 召回 → 排序 → 选 n1、n2（只解析，2-4 秒就有"随时可切"的候选）
       │     └─ 后台再把整首下到本地，落盘后回填 localURL（两段式）
       ├─ 播完（didPlayToEnd）→ 取 n1 → 本地文件起播 → 再补一首新的 n2
       └─ 用户点「下一首」→ 记负反馈 → 用已预取的 n1 顶上 → 再补一首
```

稳态是**每听一首只多下 1 首**（n1 被消费掉、补回 n2），磁盘最多留 3 个文件、`prunePrefetch` 按
「当前 + 待播」清理。没来得及预取就先解析出流地址（`pendingStream`），**不让用户干等下载**。

召回四路：**画像 top 歌手** → **一条搜索词** → **旧爱池**（收藏 ∪ 下载）→（冷启动时）**种子歌手**。
种子歌手只在画像为空时参与，避免"随手点的一首"把后面十首带偏。
前三路并发搜索，过 `DiscoverRules.pick`（原版优选、同歌手 ≤2）后打分。网络调用 ≤3 次/首。

队列语义：心动模式下的 `queue` 就是**本次会话队列**（已播 + 当前），新歌 append、`index` 跟过去，
所以「上一首」「播放列表」天然可用；`PlaybackRules.nextIndex(.heartbeat)` 是 `index+1`，末尾返回 nil
（**绝不取模回到开头**）。

### 无缝到什么程度

- 做到：**下一首已经整首在本地**，切歌那一秒不走网络；`pendingLocal` 直接把本地文件交给 `AVPlayer`。
- 没做到：**真 gapless**。`AVPlayer.replaceCurrentItem` 仍有一次极短的启动间隙（几十毫秒量级）。
  真零间隙要换 `AVQueuePlayer` 或双播放器交叉，属于另一个改动量级，没做。
- 音质：预取用 320k（图快）；起播后 `scheduleQualityUpgrade` 照旧后台升到无损——与在线起播同一条链。

### 失败降级

1. n1 没预取好 → 播完先等最多 10 秒（`isPlanning` 期间轮询）；
2. 还不行 → 现场算一首（`planOneNow`：**只解析流地址、不下载**，拿到地址立刻起播）；
3. 四级梯子全空 → **退回队列顺序**（列表继续 / 只有一首就重播），并提示「暂无新歌，先按列表继续」；
4. 播放中坏源 → `advanceAfterFailure` 优先换下一首心动候选，不烧队列。

## 7 验证边界与装机清单

CI 能证明：类型/编译通过（`build-ipa`）、四态循环与心动索引口径、通道权重顺序（30 次播放不敌 3 次下载）、
衰减、余弦、惩罚、MMR、新旧图案、理由文案（`logic-tests`）。

CI **不能**证明：真的能出声、切歌顺不顺、预取赶不赶得上、锁屏/后台是否照常。

装机按这个顺序试（任何一条不符，把现象告我，我按对应一环定位）：

1. 播放页点模式键 → 应看到「心动模式」（第 4 档，`sparkles` 图标）。
2. 切进去 2-3 秒内，标题下出现一行「正在按你的口味选歌…」/ 具体理由，右边「不感兴趣」。
3. 开「播放列表」→ 顶部应有「即将播放 · 心动模式」1-2 首，带理由。
4. 等这首放完 → **下一首应直接接上**（不是转圈十几秒）；播放页理由应换成新的一首的。
5. 连听 6 首：不应出现重复、不应连着 3 首同歌手；新旧比例与设置里的滑杆大致相符。
6. 设置页把熟悉度拉到最右 → 之后更常出现收藏/下载过的歌；拉到最左 → 全是没听过的。
7. 点「不感兴趣」→ 立刻跳下一首；再听一轮，这首与同歌手应明显变少。
8. 设置页「恢复被减少推荐的歌」→ 计数归零。
9. 飞行模式：已预取的那首仍能接上；接不上时给提示，不静默停。
10. 锁屏/后台放 2 首 → 模式仍是心动（锁屏副标题显示「心动模式」）。
11. **冷启动**：新装（或删掉重装）后先什么都不听，直接切心动 → 应放热歌榜的歌，理由显示「热歌榜第 N 名」；
    连听 5 首后，理由应开始出现「你下载过 / 收藏过 / 常听」——说明画像接管了。

## 8 已知取舍 / 没做

1. **真 gapless 没做**（见 §3）。
2. **没有跳过学习**：30 秒切歌目前只降低该次播放的"质量分"（0.3 下限），没有把"这个歌手的歌老被切"
   变成显式惩罚。要做的话在 `buildProfile` 里加 `skipArtist` 计数、在 `penalty` 里乘系数即可。
3. **冷启动走热歌榜**（见 §2.6）：没有数据时放平台官方榜单里"没听过的热门"，不说"猜"；榜单也拉不到
   （无网 + 无缓存）时才会停在当前这首并提示。
4. **「不感兴趣」会连带降权同歌手**（×0.15，永久，直到一键恢复）。这是"减少这类推荐"的口径；
   要"只屏蔽这一首"就往 `dislikedArtists` 那两行收手。
5. **搜索通道不做歌名反查**：搜索词只用来「命中歌名/歌手加分」与出理由，不会拿歌名再去搜一遍歌
   （多一轮网络，收益不如直接用歌手）。
6. **心动曲目不做"后台升档"**（2026-11-19 修）：预取是 320k，起播后**不再**替换成远端无损。
   原因是升档会 `replaceCurrentItem`，新 item 缓冲期间进度停在 0:00（录屏里那次"卡 10 秒"），
   而且升档源一旦失败/时长对不上就会触发换源 → 自动跳歌（"淋雨一直走被切走"）。
   代价：心动模式这几首是 320k，不是无损。要无损就得接受"切歌时多等一次远端缓冲"。
7. **结束通知要验明正身**：切歌后 1.2 秒内、或不是当前 item 的 `didPlayToEndTime` 一律忽略——
   这是"我没动它自己跳了"的另一半原因（旧 item 的迟到通知又推进了一首）。
