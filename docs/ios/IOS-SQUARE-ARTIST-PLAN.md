## 0 一句话

把「编辑精选」那排 4 张文字卡，换成 **歌单广场（封面墙）+ 歌手大全（头像墙）** 两个模块；
各自带整页与详情页。内容从"本地写死的 120 首"换成酷我官方数据
（**1754 张热门歌单 / 9086 张最新歌单 / 8849 位歌手**），点开即播。

| | 现在（编辑精选） | 改后（歌单广场 + 歌手大全） |
|---|---|---|
| 数据 | 本地池 4 类 × 30 首（歌名+歌手） | 酷我官方歌单 / 歌手，带 id、封面、播放量、粉丝数 |
| 点开 | 现搜 20 首（并发 3，逐行替换，可能搜不到） | 歌单/歌手自带 rid，**点开就是歌** |
| 量级 | 120 首 | 1754 + 9086 张歌单、8849 位歌手 |
| 视觉 | 4 张 186×78 文字卡 | 132 封面横排 + 64 圆头像横排；整页是封面墙 / 头像墙 |

## 1 为什么可以换（前提已变）

编辑精选的底座是 **2026-11-17 之前**的结论：「四家平台都没有歌单 / 榜单接口」。
后来酷我接口被逐条实测推翻——第二十轮的热歌榜、第二十九轮的新歌单都在用，
这个前提已经不成立。现在编辑精选反而是全页体验最差的一块：

1. **慢**：点进歌单页要 20 首逐首搜索（并发 3），首屏是"占位行 → 正式行"的替换过程；
2. **可能空**：搜不到原版的行只能留警告图标；
3. **假**：池子是写死的，一年前和今天推的是同一批歌；
4. **不好看**：四张没有图的文字卡，放在发现页最上面，撑不起"发现"两个字。

歌单广场和歌手大全补的正是这三件事：**真数据、点开即播、有图**。

## 2 信息架构

发现页自上而下（改后）：

```
① 搜索
② 歌单广场   ← 原编辑精选的位置
③ 歌手大全
④ 最近播放
⑤ 最新单曲
⑥ 猜你喜欢
⑦ 热门音乐
```

理由：先"逛"（广场 / 歌手），再"你的"（最近 / 新歌 / 推荐），最后"榜"。

「最新」承接）。

## 3 接口与数据（2026-11-18 本机实测）

全部 **匿名、https、无签名、无 cookie**，ATS 不用加例外。

| 用途 | 端点 | 实测 |
|---|---|---|
| 热门歌单 | `wapi.kuwo.cn/api/pc/classify/playlist/getRcmPlayList?pn=1&rn=30&order=hot` | total **1754**；字段 `img` / `name` / `uname` / `total`(首数) / `listencnt`(播放量) / `id` |
| 最新歌单 | 同上 `order=new` | total **9086** |
| 歌单详情 | `wapi.kuwo.cn/api/www/playlist/playListInfo?pid=<id>&pn=0&rn=100` | 104 首的示例：`musicList` 带 `rid` / `pic` / `album` / `duration` / `releaseDate`；`userName` 是创建者显示名 |
| 歌手列表 | `wapi.kuwo.cn/api/www/artist/artistInfo?pn=1&rn=30&category=<id>&prefix=<A-Z>` | total **8849**；字段 `pic120` / `pic300` / `artistFans` / `musicNum` / `albumNum` / `name` / `aartist` |
| 歌手歌曲 | `wapi.kuwo.cn/api/www/artist/artistMusic?artistid=<id>&pn=1&rn=50` | 周杰伦 total **1707**；`list` 带 `rid` / `releasedate` / `album` |

**歌手分类 id（实测 total）**：

| id | 含义 | total | id | 含义 | total |
|---|---|---|---|---|---|
| 0 | 全部 | 8849 | 1 | 华语男 | 1823 |
| 11 | 华语 | 3603 | 2 | 华语女 | 1484 |
| 13 | 欧美 | 3614 | 3 | 华语组合 | 296 |
| 12 | 组合 | 1632 | 4 | 日韩男 | 591 |
| 7 | 欧美男 | 2103 | 5 | 日韩女 | 517 |
| 8 | 欧美女 | 739 | 6 | 日韩组合 | 524 |
| 9 | 欧美组合 | 772 | | | |

字母可叠加分类：`prefix=A` → 446 位；`prefix=Z&category=11` → 336 位（华语 Z 开头）。

> **刷新时间**：这三类接口的响应里**都没有 `pub` 这类服务端日期字段**（热榜 `ksong.s` 才有）。
> 所以"当天只拉一次"的锚点只能用本地日，并跟着热门音乐那一趟一起刷新——见 §5.1。

**一个必须先说清的限制**：按曲风标签取歌单（`getTagPlayList`）匿名访问返回 `total: 0`
（网页版同样"暂无相关数据"）。所以第一版 **歌单广场只做「热门 / 最新」两个排序，不做曲风筛选**——
宁可少一个筛选，也不做一个点了没反应的假筛选。要做曲风得补签名或 cookie，失败风险高，建议不做。

## 5 状态、缓存与边界

| 场景 | 做法 |
|---|---|
| 加载 | 封面 / 头像骨架块（与现有 `SkeletonRows` 同一套灰）；已有内容时后台刷新，不闪骨架 |
| 失败 | `StatusLine.error` + 「重试」，不清空已有内容（与热门音乐同口径） |
| 空 | 一句实话（"这个分类暂时没有歌单"），不做假数据 |
| 分页 | 广场 / 歌手每页 30；页尾 spinner，到底「没有更多了」；只在内存里翻页 |
| 当天缓存 | 两个模块的**第一页**落盘（本地日），同一天再进一个请求都不发；下拉刷新强制重取 |
| 数字 | ≥1 亿 →「x.x亿」，≥1 万 →「x.x万」，否则原数；播放量与粉丝数共用 |
| 缺图 | 封面：纸卡底 + 音符；歌手：**首字圆形占位**（比音符更像头像） |
| 跨天 | 本地日切天；回前台核一次（复用第二十九轮 `scenePhase` 那一套） |
| 播放 | 歌单队列＝已加载的 100 首；歌手队列＝50 首；「播放全部」从第 1 首起 |

### 5.1 「加载一次，当天不再加载」：四个酷我模块共用一趟

老板这一条和上一轮最新单曲是同一个要求：**歌单广场、歌手大全也当天只拉一次，
和酷我接口的刷新节奏对齐**。做法是把它们并进现有的那一趟，而不是各写一套定时器：

| | 现在 | 改后 |
|---|---|---|
| 热门音乐 | 按酷我 `pub` 换榜日期判缓存；无 `pub` 时按本地日 | 不变（它是有服务端日期的那个） |
| 最新单曲 | 本地日 + 与热门同一趟 `loadDaily()` | 不变 |
| 歌单广场 | — | **第一页**并入 `loadDaily()`：当天有缓存 → 一个请求都不发 |
| 歌手大全 | — | 同上；缓存按 `category|prefix` 分键（切分类/字母才取下一份） |

- **同一趟进、同一趟出**：四个模块首屏数据由一个 `loadDaily()` 并发发起，
  下拉刷新、跨天、回前台也是同一趟一起重取——不会出现"热门换了、广场还是昨天"的错位。
  热门按 `pub` 提前换榜时，这一趟会顺带把广场/歌手也重取一次（同一次并发，不多一次往返）。
- **刷新锚点为什么是本地日**：歌单 / 歌手接口**没有** `pub` 这类服务端刷新日期（实测响应里没有），
  而 `order=hot` 的排序随播放量实时变——拿首条 `id` 当"版本号"会在一天内反复变，
  反而变成"每次打开都在刷"。所以锚点用本地日（和最新单曲同口径），
  **不自己发明一个刷新时间**。
- **可选的服务端探测**（默认关）：每天第一次进发现页时，用 `rn=1` 拉一次最新歌单首条 id，
  与缓存里记的 id 不同才重取整页（约 1KB，和热榜 `pub` 探测同一思路）。
  等真有"当天加了新歌单要立刻看到"的需求再打开。
- **缓存落盘**：`square_hot_v1` / `square_new_v1` / `artists_v1_<category>_<prefix>`，
  各存 `{day, total, items}`；第一页 30 条约 6–8KB。第 2 页起只在内存，退出页面不保留；
  下拉刷新回到第 1 页。

## 6 无障碍 / 动态字体

- 歌单卡 label：「歌单名，104 首，91.2 万播放」，hint「打开歌单」；
- 歌手卡 label：「周杰伦，166.4 万粉丝」，hint「打开歌手页」；
- chips 加 `.accessibilityAddTraits(.isSelected)`；所有可点区域 ≥ 44×44；
- **AX 字号**：名称两行封顶；到 Accessibility 档时，两个 grid 切成**单列列表行**
  （72 封面 + 文案 + 计数），避免双列被挤成四行字。这条是 R2/R3 的验收项，不是"以后再说"。

## 7 落地拆两轮（建议）

| 轮次 | 内容 | 为什么这样切 |
|---|---|---|
| **R2（下一轮）** | 歌单广场全链路：发现页模块 + 广场页 + 歌单详情 + **第一页当天缓存并入 `loadDaily()`** + 断言；删除编辑精选（`EditorPlaylistView`、`prefetchEditorSeeds`、换一批） | 一条链路一次做完，才有"点开即播"的完整体验；编辑精选必须同轮下线，否则两个入口重复 |
| **R3** | 歌手大全全链路：模块 + 大全页（分类 / A-Z 分页）+ 歌手页（播放全部 / 热门歌曲）+ **同样的当日缓存并进同一趟** | 歌手页是新页面，独立评审面；和 R2 的播放/缓存底座共用 |
| **R4（清理）** | `BakedSeedSongs` / `DiscoverCatalog`（只留 Widget 用）/ Widget 口径对齐 | 编辑精选下线后这些是死代码，单独一轮删干净 |

不建议一轮把两条链路都塞进去：两套数据、四个新页面、两套分页，评审面翻倍，
出问题也难定位是"广场"还是"歌手"。

## 8 装机验收（每轮 4 件事）

1. 发现页：搜索下面第一块是歌单广场（封面 2.5 张 + 播放量角标），第二块是歌手大全（5 个圆头像 + 粉丝）；
2. 点歌单 → 详情页：头图 / 歌名 / 创建者 / 播放量都对，点「播放全部」立刻出声；
3. 点「查看全部」→ 广场页：热门 ↔ 最新切换、双列封面、滑到底自动加载；
4. 点歌手 → 歌手页：头像 / 粉丝 / 热门歌曲，「播放全部」出声。

## 9 风险与取舍

1. **没有曲风筛选**：接口匿名不可用（见 §3），做假筛选取舍掉；真要做得补签名，风险是随时失效。
2. **Widget 会不一致**：`JZWidgets` 现在仍从 `DiscoverCatalog` 取编辑精选的 3 首；R2 删了编辑精选后，
   Widget 还显示旧池子。两个选择：R2 一起把 Widget 换成「今日新歌」前三（推荐），或先留着、R4 收。
3. **歌单可能 500+ 首**：详情页第一版只拉 100 首（一页），页尾不做"加载全部"——先避免再引一层分页。
4. **版权 / 试听**：酷我歌单里可能有 VIP / 试听曲，和现有热门、新歌走同一条取流链；失败照旧跳过，不特殊处理。
5. **编辑精选的 4 类歌单**（华语经典 / 粤语 / OST / 欧美）会消失：它们的内容质量其实不差，
   但属于"我们替用户选歌"。歌单广场是"酷我编辑选歌单"，层级更高一层；如果老板舍不得，
   可以把 4 个池子降级成广场页里的"专题"入口（不占发现页位置）。

## 10 设计自评（按两个 skill 的口径）

- **iOS HIG：9/10**。原生 push 导航、列表行、胶囊 chips、语义色、44pt 命中区、安全区都过；
  扣 1 分在"还没有真机 VoiceOver 与 AX5 走查"——方案层面补不了，得装机。
