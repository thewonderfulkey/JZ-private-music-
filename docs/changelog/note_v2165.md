## JZ 音乐助手 v2.1.65

### 一、下载列表瘦身（本次 UI 唯一改动）
每首歌下面那两行校验文字（「所选 X · 实得 Y」、体积复核说明）全部撤掉——这些是纯后端逻辑，不该占前端行高。
现在一行里只有：歌名 + 一个档位标签（无损 / 320k / 128k）+ 歌手 · 状态。校验记录仍写进 `DownloadItem.note` 落库，只是不再显示。

### 二、「320k / 128k 反而找不到」的根因

先说清一件事：**代码里没有三十多个音源**。可用的取流后端只有 4 个——

| 后端 | 平台 | 实测真实能力 |
|---|---|---|
| gdstudio | 网易 | 诚实分档：无损给 flac（786–2839kbps）、320k 真 320kbps、128k 真 128kbps |
| oiapi | 网易 | 三档都返回同一条 128k mp3 |
| 妖狐 | 酷我 | 恒无损（707–1239kbps），没有任何 320/128 字段 |
| cyapi | QQ | 域名级不可达，0 成功（`ConnectionError`） |

酷狗早在 v2.1.9 废弃（无取流后端）。所以「能真给 320k/128k 的只有网易这一条线」，而 QQ 来源的歌只能靠「跨源找到网易同曲条目」。

**真正的两个缺陷：**

1. **跨源候选排序把「同平台」排在最前**。QQ 歌的候选先把 QQ 条目发出去（cyapi 必失败，一条耗 12s 超时）、酷我歌的候选先把酷我条目发出去（妖狐只给无损，对 320/128 完全无意义）。在「每批 3 条 + 整轮 40s 预算」下，**能出 320k 的网易候选经常整批都排不到**，于是 320k/128k 表现成「找不到」。
2. **妖狐兜底在这两档上空等**。它恒给无损，320k/128k 却照样在拿到 128k 之后再去打它一次，白等 12s。

**修法**：候选排序改为「能出目标档的平台优先（网易前置，其它平台排到队尾）」，无损档仍按同平台优先；妖狐那条兜底在 320k/128k 且已有其它音源时不再空等。UI 侧不再展示校验文字。

### 三、30 首三档接口实测（口径：歌名 + 指定歌手精确锚定，逐条下载容器头 + 字节数/时长换算码率核实）

- 网易来源 10 首：**三档 10/10 全命中**（gdstudio 真 flac / 真 320k / 真 128k）
  演员、年轮、成都、凉凉、光年之外、平凡之路、起风了、童话、富士山下、后来
- QQ 来源 10 首：**三档 4/10**
  命中：江南、她说、红豆、十年（跨源到网易条目，三档全有）
  未命中：夜曲、稻香、青花瓷、七里香、告白气球、晴天（网易曲库无周杰伦版权，QQ 自身后端又不可达 → 三档都拿不到）
- 酷我来源 10 首：**三档 3/10**
  命中：爱情转移、朋友、我愿意（跨源到网易原唱，三档全有）
  未命中：月半小夜曲、千千阙歌、恋曲1990、遇见、一千年以后、小幸运、夜曲（网易侧没有同名同歌手原唱）

小计：**无损 17/30、320k 17/30、128k 17/30**——三档数字完全一致，这本身就是结论：能不能拿到 320k/128k，取决于「这首歌在网易有没有原唱」，跟哪个平台来的无关。

而你看到的「无损几乎都能下」，是妖狐兜底撑起来的：它对 QQ/酷我来源的歌恒返无损，把「有文件」兜住了，但兜出来的只有无损。所以现象就是「无损普遍有、320/128 大面积没有」。
