# v2.1.79 去掉进度条 + 逐字染色改按「真实逐字时间」

先直接回答你最后那个问题：**不需要换源、也不需要另外找"带每个字时间的精准歌词文件"——现在用的歌词源里本来就有。**

## 一、逐字时间一直在手边，是我们在解析时把它丢了

用本机直连酷狗歌词接口实测《暗号》（周杰伦），取到的是 KRC（`contenttype=0`），明文里每个字都自带毫秒级的起点与时长：

| 字 | 相对行首起点 | 时长 |
|---|---|---|
| 我 | 0 | 156 |
| 想 | 156 | 153 |
| 要 | 309 | 198 |
| 的 | 507 | **457** |
| 想 | 964 | 223 |
| 做 | 1187 | 194 |
| 的 | 1381 | **524** |
| 你 | 1905 | 218 |
| 比 | 2123 | 248 |
| 谁 | 2371 | **545** |
| 都 | 2916 | 382 |
| 了 | 3298 | 193 |

同一行里最短 153ms、最长 545ms，**相差 3.6 倍**（统计 8 行：1.0× / 1.0× / 3.6× / 3.4× / 2.8× / 1.5× / 1.2× / 1.5×）。这就是"按字数均分"一定对不上的直接证据：一旦遇到拖长音，字明明还在唱，均分已经把进度推到后面去了；遇到快唱，字已经唱完，均分还在慢慢爬。

以前工程里 `krcToLrc()` 把每个词条的 `文字` 拼起来、只保留**整行**时间戳，逐字时间就在这一步被压平丢掉了。所谓"只能拿到整行时间的 LRC"是我们自己降级的结果，不是数据源的限制。

## 二、你看到的两个症状，是三条原因叠在一起

1. **分母取到了下一行**：旧 `ratio = (pos - lineStart) / (nextLineStart - lineStart)`。句尾的休止、句中的间奏全算进这一句的"时长"里，于是"歌词唱完了，条还没满"。
2. **行内线性均分**：见上面的 3.6 倍差，局部必然超前 / 滞后。
3. **数据侧丢了逐字时间**：见第一节。

## 三、这版改了什么

**数据层**

- `LyricsService`：新增 `LyricWord(text, startMs, durMs)`；`LyricLine` 增加 `words`（默认空集合，所有旧调用点不用改）；把逐行清洗抽成公开 `cleanLine()`，LRC 与逐字解析共用同一口径。
- `LddcCrypto`：新增 `krcToLines()` —— 词条 `<start,dur,offset>文字` 的 `start/dur` 是**行内相对毫秒**，这里统一换算成 **`行首 + 相对` 的整首绝对毫秒**；新增 `qrcToLines()` —— 词条 `文字(start,dur)`，带自适应基准（首词时间小于行首就按行内相对加行首）。旧的 `krcToLrc` / `qrcToLrc` 保留作兜底。
- `LddcLyrics`：`fetchKgLines` / `fetchQqLines` 直接返回带逐字时间的行列表；KRC 解析不出逐字时退回整行 LRC，QRC 同理。损坏校验改为对拼接文本做，行为不变。

**视图层（`DesktopLyricsView`）**

- **底边进度条整段删除**：`drawProgress()` 函数、它的调用、`LinearGradient` / `Shader` 两个 import 全删；栏体底边预留从 16dp 收紧到 10dp，文字块更居中。
- 新增 `setWordTiming(words)` / `setPosition(ms)`：视图直接拿"当前播放位置"和"每个字的绝对起止"比对。
- `buildCharTimes()` 把逐字时间映射到当前句的每个字符上：空格只带宽度、不占时段；**只有每个可见字都拿到时间才算可用**，映射不全就整行退回行内插值（宁可粗一点，也不要错亮）。
- `charFill(i)`：`pos < 起唱 → 0`，`pos ≥ 唱完 → 1`，中间按 `(pos - 起唱)/时长` 连续压深。**句子最后一个字唱完立刻整句全亮，不等下一行**——间奏期间不会再出现"没染满"。

**时钟层（`DesktopLyrics`）**

- `tickOnce()` 先推新句的逐字时间、再换文本，保证换句那一帧映射已对齐；`setPosition(pos)` 每拍（100ms）更新；只有**该曲没有逐字时间**时才走旧的 `setKaraoke(ratio)` 回退。

## 四、验证

- 静态验证（`apk-verify` 口径）：**62 项，61 PASS，1 缺口**（`adb devices` 恒为空，本机无设备/模拟器，真机冒烟做不了）。版本 vc137 / 2.1.79，包名 `com.jz.musichelper`，签名 v2 校验通过，zip 183 条目完整。
- **真实数据回归**（不是只看编译过）：用同一首《暗号》的实时 KRC 明文，按与 Kotlin 侧同一套正则 / 同一换算复算，**22 项全 PASS**：
  - 49 行全部带逐字时间；`16211ms` 那行 12 个词条、首字绝对时间 = 16211、末字结束 = 19702；
  - 逐字→字符映射 0 个未映射；
  - 播放到 `17000ms` 时：我 / 想 / 要 全亮、「的」62%（与实测时间表逐字吻合）；
  - 播放到 `19900ms`（句已唱完、仍在间奏、下一行还没到）：**12 字全亮**；
  - 同一时刻的"均分"口径只到第 2.71 个字——两者差 0.8 个字，正是你看到的"慢半拍"。
- QRC 用合成样本验了两种时间基准（绝对 / 行内相对）都能正确换算、文本能正确拼。

**缺口（说清楚）**：没有真机，逐字观感需要你装机确认；QQ 的真实曲这轮没跑通（缺真实的 QRC 密文样本，只用合成样本验了解析逻辑）；纯 LRC（无逐字时间）的曲子只能退回行内插值，会比这版慢一点，但不会再"卡在没染满"。

## 五、你可以这样自查

1. 装 v2.1.79，开桌面歌词，播一首**有间奏**的歌（《暗号》第 16–20 秒那段就是典型）。
2. 盯句尾：最后一个字唱完，整句应立刻全亮；间奏期间保持全亮，不会慢慢补。
3. 盯拖长音的字（比如"谁"545ms 那种）：该字应匀速压深，而不是被后面几个字赶超。
4. 换一首只有整行时间的曲子：仍能跟播，只是回到"匀速推开"，不会卡死。

## 六、口径提醒

- 逐字染色**以歌词源自带的时间为准**。如果某首歌的音频是翻版 / 变速版，而歌词是原版时间轴，那会整体偏移（不是均分问题），那需要另做一个"歌词延迟 ±"调节项，这版没做。
- 底边进度条是**按你的要求彻底移除**，不是隐藏；栏体因此略微变矮。
- 字体、三套纸色、工具条、字号档位、锁定、拖动吸边等行为均未改动。
