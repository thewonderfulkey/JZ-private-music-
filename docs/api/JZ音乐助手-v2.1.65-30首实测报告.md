- 版本：versionCode 123 / versionName 2.1.65
- 包体：29,585,055 B（28.2 MB）· MD5 `AC1F32320435A68EA2E474E09762128E`
- 实测时间：2026-11-09
- 说明：本轮所有结论都来自「真实请求 + 文件实测」，不依赖接口自报的档位字段。

---

## 一、先纠正一个前提：代码里没有三十多个音源

可用的取流后端只有 4 个，全部在 `SourceAdapters.kt` 里注册：

| 后端 | 平台 | 端点 | 实测真实能力 |
|---|---|---|---|
| `GdstudioNeteaseAdapter` | 网易 | `music-api.gdstudio.xyz` | **诚实分档**：`br=740` 给 flac（786–2839kbps）、`br=320` 真 320kbps、`br=128` 真 128kbps |
| `OiapiNeteaseAdapter` | 网易 | `oiapi.net/api/Music_163` | 三档（standard/exhigh/lossless）返回**同一条 128k mp3** |
| `YaohuKuwoAdapter` | 酷我 | `api.yaohud.cn/api/music/kuwo` | **恒无损**（707–1239kbps），返回体里没有 320/128 字段 |
| `CyapiQQAdapter` | QQ | `cyapi.top/API/qq_music.php` | **域名级不可达**，10/10 全部 `ConnectionError` |

搜索侧的 3 个适配器（QQ `client_search_cp`、网易 `/api/search/get`、酷我 `r.s`）只负责找歌，不给音频。
酷狗在 v2.1.9 已废弃（从来没有取流后端）。

**结论**：能真正产出 320k / 128k 的只有网易那一条线（gdstudio）。QQ 来源的歌只能靠「跨源找到网易同曲条目」这一条路。

另外排查了 10 条外部候选通道，全部不可用（详见第七节）。

---

## 二、根因（两层，代码 + 实测共同支撑）

### 第一层：通道能力本身是偏的
- 320k/128k 只有 gdstudio 能给，且只覆盖网易曲库；
- QQ 平台没有任何可用取流后端；
- 妖狐恒给无损 —— 它把「有文件」这件事兜住了，所以无损看起来「几乎都能下」；
- 网易无版权的歌（周杰伦全系），320k/128k 天然没有。

### 第二层：跨源候选排序把预算喂给了错误的平台（本次修的就是这个）
`SameSongCrossResolver.resolveForDownload` 原来的排序是：

```
compareBy { if (it.platform == song.platform) 0 else 1 }.thenByDescending { studioScore(it) }
```

「同平台优先」。于是一首 QQ 歌的候选里，QQ 条目先被批量发出去（cyapi 必失败，**一条耗满 12s 超时**）；一首酷我歌的候选里，酷我条目先被发出去（妖狐只给无损，对 320/128 完全无意义）。

而整轮硬超时是 **40s**、每批 **3 条** ——40s 只够跑 3 批左右。**能出 320k 的网易候选经常整批都排不到**，于是 320k/128k 就表现成「找不到」。

### 第三层：妖狐兜底在 320/128 上白等
妖狐恒给无损，但 320k/128k 时只要还没拿到目标档就照样再打它一次，又白等 12s。

---

## 三、修复内容（v2.1.65）

1. **候选排序改为「能出目标档的平台优先」**：320k/128k 时网易候选前置，QQ/酷我 候选排到队尾；无损档仍按同平台优先（同平台换源更稳，且妖狐恒给无损）。
   `SearchAndResolve.kt` 新增 `tierCapable(platform, want)`：无损 = 全平台可；320k/128k = 仅网易可（依据实测）。
2. **妖狐兜底收敛**：320k/128k 且前两轮已有任何音源时，不再打第三轮（省 12s）；无损档行为不变。
3. **下载列表瘦身**：去掉每首歌下面那两行校验文字（「所选 X · 实得 Y」、体积复核说明），行内只留歌名 + 档位标签（无损 / 320k / 128k）。校验记录仍写 `DownloadItem.note` 落库，不展示。

## 四、30 首实测（口径：歌名 + 指定歌手精确锚定）

判定方式：拿到 URL 后 `Range` 拉 4KB 读容器头（flac / mp3 / m4a），再用「文件总字节 ÷ 歌曲时长」换算真实码率，按 `QualityFacts.matches` 判档。
- 无损 = flac/wav 容器 或 ≥600kbps
- 320k = 非无损容器且 256–600kbps
- 128k = 非无损容器且 48–255kbps

## 七、已排查、确认不可用的外部通道（10 条，勿再试）

| 通道 | 结果 |
|---|---|
| gdstudio `source=tencent/kuwo/kugou` | HTTP 400 `Value of source is not supported`（只支持 netease） |
| gdstudio `source=netease&id=<QQ mid>` | 200 但 `url` 为空 |
| 妖狐 `api/music/qq` | 400 `参数 action 未配置` |
| 妖狐 `api/music/netease`、`api/music/wy` | HTTP 525 |
| 酷我官方 `mobi.kuwo.cn` `convert_url2`（320kmp3/128kmp3/flac） | 全部 HTTP 404 |
| 酷我 `convert_url3` | 返回直链但实测 0 字节 / 超时 |
| 酷我 `antiserver.kuwo.cn/anti.s` | 200 给 mp3 直链，但总字节仅 181,521（约 6kbps 试听片段） |
| 酷我 `www.kuwo.cn/api/v1/www/music/playUrl` | `The request is illegal!`（首页 500、无 kw_token） |
| `api.qq.jsososo.com` / `api.injahow.cn/meting` | ConnectionError / 200 空响应 |
| `api.vkeys.cn/v2/music/tencent` 与 `.../netease` | 只给「音乐试听」24–34kbps / `url:null` |

> 补充事实：酷我曲库本身**有 320k 资产**（「稻香 周杰伦」的 `FORMATS` 含 `MP3H`），只是没有可用 API 把它取出来。若后续能拿到酷我 320k 直链，QQ/酷我 侧的 320k 才可能真正补齐。

## 八、结论

1. 「三十多个音源」与实际代码不符：只有 4 个取流后端，其中 1 个（QQ）完全不可达。
2. 320k/128k 大面积失败的直接原因，是**跨源候选排序把 40s 预算喂给了给不出该档的平台**，已在 v2.1.65 修正。
3. 修完之后仍会有一批歌拿不到 320k/128k —— 那是**网易曲库没有该曲原唱**（周杰伦全系最典型），属内容版权边界，不是程序缺陷；此时 App 会如实降级为无损并在后端留痕。
4. 下载列表的校验文字已按「纯后端逻辑」处理：只落库、不展示，歌名后保留一个档位标签。
