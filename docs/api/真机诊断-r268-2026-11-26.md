**六条腿全空，没有一条"被闸拒"，是根本没搜到。**
根因：平台把歌手写成上传者 `小酒`，而版本信息塞在歌名括号里；用「原名 + 小酒」搜谁都搜不到。
老板验证：换成「茶花开了，该回家了」+「王睿卓&加木」就能拿到。

修复（`84a2794`）：`SearchQueryVariants` 生成有序搜索词（原名 → 去括号 → 去括号+括号歌手 → 只留歌名），
最多降级 2 次；身份闸补一条「歌手对不上原名、但对上括号里的歌手也算同一条录音」。
接入：跨平台检索 + 妖狐酷我（按歌名搜的腿）。

### 2.2 进度条时间不对：条走完、剩 0:00、还在唱

不是播放器的问题，是**总长被锁错**：
`adoptDuration` 会把播放器第一次报的时长锁死；在线流没有可信总长时，那个值可能偏短（VBR mp3 没 Xing 尤其明显），
于是条提前到 100%，而 `到点收尾` 因为 `durationVerified=false` 不会触发 → 歌继续唱。

**第一版修法（已废弃）**：播放中若 `currentTime > duration + 0.5` 就把总长顶上去。
老板否了——这是"播过头再改数"，治不了根，而且会让进度条中途跳一下。

**最终修法（`0bb7ce1`）**：**过闸时就把文件自证的时长拿到，起播前写进播放器**。
`PlaybackCache.probe` 本来就取了头部 128KB 解时长，只是没往外传；现在 `Probe.durationSec`
→ `GateResult.durationSec` → `start(trustedDuration:)`，进度条从一开始就是对的，不需要中途纠正。
剩余时间在没有可信总长时显示 `--:--`（诚实），不再报一个可能是错的数字。

已知边界：文件头解不出时长的那一小撮（实测 MP3 6%、M4A 的 moov 在文件尾）仍无可信总长，
下一步补"读文件尾 1MB"。

### 2.3 进度回退误报

`Kiss 4s → 0s` 这类是换歌瞬间的迟到旧进度。改成同一 item 内**连续两拍**都低于前值才记账（`84a2794`）。

## 三、红颜「同曲重装」是用户行为，不是违规

```

16:14:19.719  item 替换  红颜 ← 播放缓存 ... 本曲第2次（同曲重装）
```

用户在同一首上又点了一次。分析脚本后续会把「重装前 2 秒内有 goTo」标成「用户重选」，不计 R1 违规。
