# MobiMusic 逆向报告对照：我们缺什么、该补什么

- 输入：`MobiMusic-APK逆向与API连通性报告.md`（2026-11-25，59 项实测通过 45 项）
- 本文口径：**只做缺口评估与建议，不落码、不出包**
- 目标：老板定的「稳」——一条腿断了，别的能接住
- 对照对象：`ios/JZMusicHelper`（12 条取流腿）、`desktop/` 与 `android/`（各 5 条取流腿）
- **后续实测**：本文的推断已在 `docs/api/线路基线实测-2026-11-26.md` 逐条验证。
  实测修正了两处：① 网易官方在匿名下对 VIP 歌 **0/11**（只对免费歌有效）；② oiapi 是「假活」——
  给 URL 但只有 30 秒试听，比死腿更坑。看本文时请对照那份实测。

---

## 0 一句话结论

MobiMusic 强在「**播放地址层可以由用户换掉**」，弱在「一堆内置服务是死的还得靠用户自备」。
我们反过来：**播放链、缓存、身份校验比它硬**，但有四处结构性短板——

1. **发现页/广场/榜单/歌单详情，四个页面共用酷我一家**（单点）
2. **取流腿多，但八条是同一类第三方聚合站**（同一批货源、同一批 key，会一起死）
3. **换源必须发版**（域名/key 全编进二进制，用户装的是自签包，升级很痛）
4. **腿断了看不见、也没有统一判死口径**（我们已经在 oiapi 上栽过一次）

前三条会直接导致「全 App 没内容」，第四条例决定「一条腿偶尔抖动会不会被误杀 15 分钟」。

## 1 MobiMusic 是什么结构（三句话）

1. **元数据直连四家非官方 Web 接口**（网易/QQ/酷我/酷狗，外加 B站、iTunes），不要后端。
2. **播放地址层外挂**：Dart 里查不到任何 `player/url`/`vkey`，全由用户导入的洛雪（LX）音源脚本算出。
3. **自建后端只做账号**，且挂了不影响听歌（522 实测，App 照用）。

它 76% 的通过率里，死掉的全是「需要有人运维的东西」：自建后端 522、内置音源服务 TCP 超时、
第三方 AI 代理 TLS 被 reset、Odesli 公开入口废弃、smartall 要 Bearer。

**规律：凡是「我们自己运维的」和「别人白给的」，都会死；只有「各家官方匿名接口」活得久。**

## 2 我们现在的位置

### 2.1 能力对照

| 层 | MobiMusic | 我们 iOS | 我们 桌面 / Android |
|---|---|---|---|
| 搜索 | 4 家 + B站 + iTunes | 4 家（+ meting 补充） | 4 家 |
| 详情/专辑 | 网易为主 | 网易 + 各平台 | 同 |
| 歌词（逐行） | 4 家 + AMLL TTML | **6 条腿**（lrclib/网易/酷狗 LDDC/酷我/QQ/网易官方） | 同（LDDC 算法在本仓） |
| 歌词（逐字） | 脚本层 + TTML | **KRC + QRC 两条** | 同 |
| 封面 | 4 家 + iTunes | 4 条腿 + 本地旁车 | 同 |
| **榜单** | 网易 toplist / 酷狗 rank | **只有酷我** | **没有榜单接口**（种子词搜索拼的） |
| 歌单广场/歌单详情 | 脚本层 + 第三方 | **只有酷我** | 同 |
| 取流 | LX 脚本（用户可导入） | 12 条（其中 8 条第三方聚合站） | **5 条**（全是第三方聚合站 + 酷狗官方） |
| 识曲 | ACRCloud + Audd | 网易 audio/match + 酷狗指纹 | 同 |
| 跨平台补源 | 无（脚本只换 URL） | **SameSongCrossResolver**（同曲换平台） | 同 |
| 后端熔断 | 未提（脚本自己重试） | BackendHealth 冷却表 | 无 |
| 本地兜底 | 下载 + 缓存 | 缓存 + 下载 + 完整性五道校验 | 同 |

### 2.2 我们已经比它强、别改坏的四件事

1. **跨平台同曲换源**：它只能「同一个 songmid 换 URL」，我们能「换一个平台再找同一首歌」。这是它没有的最后一招。
2. **身份优先于音质**：v2.4.117 的排序改造（`DownloadResolver.Score.identity` 第 0 位）挡住了「众/侧脸」串歌。
   多补源时**不许为了凑数放松这条闸**，否则补得越多越容易串。
3. **不信自报、只认实测**：`StreamVerifier` + `QualityFacts` 用 Range 探真容器与真实码率。
   MobiMusic 报告 §4.2/§4.4 反复强调「接口说的不算」，我们已经是这个口径。
4. **下载完整性五道校验 + 判死名单**（v2.4.120/121）：它完全没有。

## 3 四个真缺口

### 缺口 1（P0，最便宜）：发现 / 广场 / 榜单 / 歌单详情，四个页面共用酷我一条腿

**现状（代码事实）**

- `Services/DiscoverFeed.swift`：热门音乐首选 `KuwoChart`（`wapi.kuwo.cn/api/pc/bang/list` + `kbangserver.kuwo.cn/ksong.s`）
- `Services/SquareFeed.swift` + `KuwoPlaylist.swift`：歌单广场、每日最新单曲、歌单详情，全走 `wapi.kuwo.cn`
- iOS 侧兜底是「6 个种子词 → 四平台并发搜索」，桌面的热门本来就是这条路

**问题**：酷我只要对这台机器/这个时段限流一次，**四个页面同时空**。我们已经在妖狐那儿见过 403 持续 25 分钟不解封。

**MobiMusic 给的现成答案（报告 §4.1，均实测 200、无需 key、无需签名）**

| 用途 | 端点 | 报告实测 |
|---|---|---|
| 网易榜单 | `music.163.com/api/toplist` | 200 / 84 KB |
| 网易首页块 | `music.163.com/api/homepage/block/page` | 200 / 200 KB |
| 网易歌单列表 | `music.163.com/api/playlist/list?cat=&limit=` | 200 |
| 酷狗榜单 | `mobiles.kugou.com/api/v3/rank/song`（**别用报告里的 `mobilecdnbj`**） | 200 / 500 首 |

> 酷狗域名要用 `mobiles.kugou.com`：`mobilecdnbj.kugou.com` 我们 2026-11-16 就因为证书不匹配在 iOS ATS 下弃用了
> （见 `docs/ios/IOS-NETWORK.md` §3.3）。

**补法**：榜单/广场各加两条独立腿，按「榜名映射」合并（酷我热歌榜 ↔ 网易云音乐热歌榜 ↔ 酷狗 TOP500），
解析失败就退回现有种子词搜索。**不新增任何 UI，不改播放链。**

**收益**：四个页面从 1 条腿变 3 条腿，成本最低、风险最低。

### 缺口 2（P0）：取流腿多，但血统单一；三端还不齐

**现状**

- iOS `SourceAdapters.swift` 注册 12 条：`CyapiQQ` / `LuoyueQQ` / `NeteasePlayer` / `Gdstudio` / `Oiapi` /
  `YaohuKuwo` / `KuwoOfficial` / `IkunKuwo` / `XinghaiKuwo` / `XinghaiKugou` / `MetingNetease` / `KugouPlayInfo`
- 其中 **8 条是第三方聚合站**（cyapi / gdstudio / oiapi / yaohu / ikun / 星海 / meting / 落月），
  共同点：共享 key、同一批上游、同一个运营圈子。报告 §7 也印证「活下来的只有 zddyr / haitangw /
  wwwweb / vkeys / 103.79.184.97 这一批」——**它们会一起死**（11-20 落月风控就是一次预演）。
- 真正的「第一方」只有三条：网易官方 `enhance/player/url`（匿名可用，部分歌要登录态）、
  酷我官方 `antiserver/anti.s`、酷狗官方 `getSongInfo`（常回无 url）。**QQ 没有第一方腿。**
- 桌面/Android 只有 5 条，且**没有**落月 / 星海 / ikun / meting / 网易官方，
  所以同一首歌「iOS 能播、桌面不能播」是必然的。

**补法（按确定性排序）**

1. **三端对齐**：把 iOS 那 7 条搬进 `desktop/` 与 `android/` 的 `SourceAdapters`。纯拷贝 + 各自断言，不碰播放器。
2. **补第一方腿**：QQ 官方（`u.y.qq.com/cgi-bin/musicu.fcg` 匿名 200 可搜，但取流要 vkey，多半需登录态）
   —— **这条先验证再决定，不要在报告里当成已成立**。
3. **不引入 LX 脚本运行**：2026-11-20 已评估（`docs/api/星澜音源StellarWave-解析与连通性测试报告.md`），
   结论仍成立——LX 音源只有 `musicUrl`、没有搜索/歌词/封面；6 个平台只有 4 个活；货源与我们高度重合；
   三端都要自建 JS 运行时；脚本里硬编码别人的付费卡密，合规面脏。**不做。**

### 缺口 3（P0，架构级）：换源必须发版

**现状**：所有端点、key、开关、超时都编进二进制（`SourceAdapters.swift` 里 12 个 URL 常量）。
任何一家换域名、换 key、关站，流程是：改码 → CI → 出 IPA → **用户手动重装**。
我们不是 App Store 分发，这一步的成本比正常 App 高得多。

**MobiMusic 的等价物**是「用户自己贴脚本」——我们不做脚本，但可以只做**纯数据配置**。

**补法：远端「线路清单」（remote line list）**

- 启动时拉一份静态 JSON（GitHub raw / Cloudflare Worker），内容只有四类字段：
  `baseURL`、`参数模板`、`启用位`、`优先级顺序`；拉不到就用**内置同一份**做兜底（内置永远是保底，不是主路径）。
- **硬约束**：远端只能改「地址 / 开关 / 顺序 / 超时」，**不许改判定阈值**
  （身份闸、时长容差、码率区间、判死规则一律留在本地常量里）。否则等于远程改行为，出问题没法复现。
- 只允许 HTTPS + 版本号单调递增（防止降级投毒）；解析失败一律回内置。
- 界面上要能看到「当前用的是内置清单还是远端清单、远端版本号、上次拉取时间」，否则出问题又是一场猜谜。

**收益**：一条腿换域名，全网几分钟内自愈，不用出包。这是「稳」的最大杠杆，且不执行外部代码，合规面干净。

### 缺口 4（P1）：腿断了看不见，判死口径也不统一

**现状**

- 有 `BackendHealth`（`PlaybackRules.swift:311-400`）：403→900s、110001→300s、429/503→120s，落 UserDefaults；
- 有「播放诊断」页（只读、可复制、`诊断/trace.log`）；
- 没有**按线路汇总**的视图：哪条腿今天失败几次、上次成功是几点、冷却到几点、实测码率掉到多少。

**我们踩过的坑（必须写成规则）**：2026-11-25《众》——
`oiapi` 的 `data` 是字典，代码只认数组，于是从接入那天起**一次都没成功过**，却被记成「通道失效」。
教训原话：**「接口没给 url」≠「通道死了」，判死前必须打出真实响应（原始 JSON + 形状）。**

**补法**

1. **判死三态**：`可用` / `暂时失败（可重试）` / `判定死亡（需证据）`。
   只有第三态才允许进冷却表和下载判死名单，且必须同时留下：状态码 + 原始响应前 512 字节 + 解析形状。
2. **连续失败才降权**：单次超时不降权（现在是「一次 parse 失败就记一笔」），要 N 次/跨 M 分钟。
3. **设置页加「网络自检」**：对每条腿打同一首固定探针曲（《晴天》），并发跑，显示
   通过 / 延迟 / 实测码率 / 冷却剩余；一键导出诊断。
   我们已有 `tools/ios/probe_network.py` 和 `StreamVerifier`，做成 App 内一页是顺手的事。
4. **只读优先**：自检页第一版只显示，不提供「手动禁用某条腿」，避免又多一个状态。

**收益**：出问题 30 秒定位，不用「再出个包试试」。

### 缺口 5（P2，可选，要花钱）：识曲只有两条腿，且都在国内

- 现状：网易 `api/music/audio/match`（afp wasm + WKWebView）+ 酷狗 `gateway.kugou.com/fingerprint...`。
  两条都是非官方、都要签名，且同属国内链路。
- MobiMusic 给的备选：**ACRCloud**（`identify-cn-north-1.acrcloud.com/v1/identify`，实测服务可达，
  需 multipart + HMAC-SHA1，**要付费 key**）。
- 判断：这是「花钱买稳」的决策，不是技术问题。ACRCloud 是商业服务，稳定性高于非官方接口。
  Audd 要 token 且免费额度低，Shazam 非官方签名复杂 —— 都不建议。
- 建议：**先记着，不排期**。识曲失败是「重试一次」的体验问题，不是「全 App 没内容」的可用性问题。

## 4 建议补的清单（等拍板）

| 优先级 | 补什么 | 为什么 | 成本 | 风险 | 验证口径 |
|---|---|---|---|---|---|
| P0 | 榜单/广场加网易 + 酷狗两条腿 | 四个页面现在共用一条腿 | 低（匿名 GET，现成解析风格） | 低，不动播放链 | 三条腿各打 3 首，比对榜名与首条；断一条仍出内容 |
| P0 | 桌面/Android 补齐 iOS 那 7 条取流腿 | 同一首歌三端结果不一致 | 中（拷贝 + 各自断言） | 中，需重跑各端断言 | 同一首《晴天》三端后端列表与实测码率一致 |
| P0 | 远端线路清单（只下发地址/开关/顺序） | 换源不发版，全网几小时自愈 | 中（含签名/回滚/内置兜底） | 中，需严格约束「不许改阈值」 | 把某条腿指向坏地址 → 自动回内置、仍能播 |
| P1 | 判死三态 + 证据留存 + 连续失败降权 | 防「好腿被误杀 15 分钟」 | 低（规则 + 断言） | 低 | oiapi 那种「字典当数组」的响应必须被判成「暂时失败」而不是死亡 |
| P1 | 设置页「网络自检」 | 出问题 30 秒定位 | 低-中（复用 probe + StreamVerifier） | 低（只读） | 12 条腿并发出结果，含冷却剩余 |
| P2 | 逐字歌词第三条腿（AMLL TTML） | KRC/QRC 都在酷狗/QQ 自家 | 中 | 低 | 冷门歌/外语歌逐字命中率提升 |
| P2 | 识曲第三条腿（ACRCloud） | 两条腿同属国内非官方 | 中 + 付费 | 低 | 同一段录音三家结果一致率 |
| P3 | 封面 CDN 多域名轮换（p1/p2/p3/p4） | 一条腿变四条，零成本 | 极低 | 极低 | 单域名 404 时自动换下一个 |

## 5 明确不补（附理由，避免重复讨论）

| 不补 | 理由 |
|---|---|
| 嵌入 LX 脚本运行时 / 用户导入脚本 | 11-20 已评估：只有 `musicUrl`、无搜索/歌词/封面；6 平台 4 活；货源重合；三端要 JS 沙箱；脚本带别人付费卡密 |
| 自建云端后端（云歌单/账号） | MobiMusic 的 522 是活教材。要备份走 iCloud / 文件导出，别新增单点 |
| B站作为第五平台 | 搜索匿名可通，但 `playurl` 要登录态 + wbi；拿到的多半是 128k 视频音轨，版权面更脏 |
| 咪咕 / 汽水 | 星澜实测咪咕 0/4、汽水 0/2 |
| 评论 / 动态 / 歌单分享 | 不是「稳」的问题，是「加功能」，别混进这轮 |
| 播放中换源升档 | 2026-11-22 已叫停（卡开头）。维持「起播前一次挑好，起播后不换源」 |
| 为凑源数放松身份闸 | 会直接复活「众/侧脸」串歌。补源必须过 `identity` + 时长 + 容器三闸 |

## 6 建议的落地顺序（等点头再动）

**阶段 0（不出 App，只测量）**：写一个「按腿打表」的探针脚本（不进 App），
输出 `腿 × 3 首歌` 的成功率 / 延迟 / 真实码率 / 失败原文。
先拿到「现在到底几条腿活着」的基线——没有基线，后面补什么都是凭感觉。

**阶段 1（不碰播放器）**：榜单/广场第二、第三条腿 + 判死三态规则。

**阶段 2（架构）**：远端线路清单（先只覆盖取流腿，不覆盖元数据）。

**阶段 3（可选）**：网络自检页、TTML 逐字、ACRCloud。

每一步都能单独回滚；播放器内核、身份闸、下载校验这轮**一律不碰**。
