## 三、根因：三段接力，每段从零重发

旧解析顺序：`① startPick 窗口 2.6s（+1.2s 低档宽限）→ ② firstPlayable 6s → ③ plan 15s`。
**每段都会重新发一遍请求**——上一段在飞的请求被整组取消。

对账（用代码里的常量）：

| 实测 | 拆解 |
|---:|---|
| 3.8s | 2.6 + 1.2（窗口等到高档） |
| 7.6s | 2.6（①空）+ 5.0（②拿到） |
| 11.1s | 2.6 + 6.0（①②都空）+ 2.5（③拿到） |
| 19.0s | 2.6 + 6.0 + 10.4（③拿到） |

所以慢的不是网络，是**我们重跑了三遍**。而且旧路径还有第二处重跑：
`startRemote` 里时长闸不过时会 **再次调用 `resolveStream`**（最多 4 次）。

## 四、改成什么样（c19a420）

老板口径：「任务可以是同一个，谁先回来**并且通过校验**的谁先播放」。

- **一次解析**：所有主腿同时开跑，每条回来的先过四道闸（身份/可用/整首性/同一份文件），
  第一个全过的立刻起播，其余取消；被拒的只记一行，**不重启**。
- **在线不等档位**：先过闸的是 97k 就播 97k，不为 320k 多等——「快速播放优先」。
- **音质只在预取里比**：预取有 20–30s 预算，用 `bestValidated` 挑最高档落缓存，
  所以自动连播仍然能拿到 320k，且切歌 0.1s。
- 时长闸搬进解析准入，`startRemote` 不再二次探测/重解析。

预期：手动选歌从 P50 4.6s → **约 1s 级**（首个过闸即起播），最坏 8s（预算）。
